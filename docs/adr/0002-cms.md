# 0002 — CMS and media storage

- **Status:** Accepted
- **Date:** 2026-08-15
- **Related:** [0001-stack.md](0001-stack.md), [0004-verification.md](0004-verification.md),
  [0005-repository-visibility.md](0005-repository-visibility.md),
  [../ops/cms-runbook.md](../ops/cms-runbook.md),
  [../../design/content-model.md](../../design/content-model.md)

## Context

Non-technical members must be able to edit this site without GitHub accounts. That rules
out a purely git-backed content model, however much simpler it would be to hand over.

The site is bilingual, Turkish and English, with both locales first-class — see
[../../design/i18n.md](../../design/i18n.md). Translation is not a bolt-on here; it is a
daily editing activity, and the CMS's handling of it determines whether the Turkish half
of the site stays alive after the person who cared about it graduates.

The cost of any database-backed CMS is that content lives on a server that must keep
running, owned by someone who will eventually leave. The decisions below are arranged
around making that survivable rather than around making it pleasant.

## Decision

### 1. Strapi 5, self-hosted, Community Edition

MIT-licensed and free: no seat fees, no API call limits, no content caps. Chosen because
non-technical members must edit without GitHub accounts, and because **i18n is built into
Strapi 5's core** rather than being a plugin or a workaround — the Content Manager gets a
locale drop-down per content type, which is exactly the affordance a bilingual editing
workflow needs.

Version note for whoever reads this later: as of 2026-08-15 the current release is
v5.50.2 (July 2026), and **there is no Strapi 6**. Strapi publicly committed to stability
over a major version bump for 2026. So "Strapi 5" is not a pin against a newer option — it
is the current line. If you are reading this in 2029 and a v6 exists, treat migration as
its own change proposal, not as routine maintenance.

### 2. The three survival rules

None is negotiable. Each one exists because of a specific way this arrangement kills
websites.

**Rule 1 — No runtime dependency.** Covered by the rendering rule in
[0001-stack.md](0001-stack.md). Strapi being down means "nobody can edit today," never
"the site is offline." This rule governs media as well; see decision 5. Note the honest
limit recorded in 0001: the *build* still depends on Strapi even though the request path
does not.

**Rule 2 — Scheduled export back into the repository.** A GitHub Action runs Strapi's
export on a schedule and commits the dump to `content/_snapshots/`. This restores the git
history and handover safety that a database-backed CMS otherwise costs us. It is part of
CMS setup, not a later chore. **Data only, never media, never drafts, never Alumni** — the
last two are required by the KVKK section below and are not adjustable.

Three mechanics that are easy to get wrong and expensive to discover later:

- The workflow **file** lives on `main`, because GitHub only fires `schedule` triggers
  from the default branch. It **commits to a dedicated `content-snapshots` branch**, never
  to `main`.
- Committing to `main` would trigger a production deploy on every export, turning the
  backup into a scheduled site rebuild — which is the timed rebuild
  [0001-stack.md](0001-stack.md) forbids. The dedicated branch avoids this without needing
  build-ignore configuration that a future maintainer would have to discover.
- Because the snapshots are not on `main`, **someone cloning the repository sees no
  backups at all**. [../HANDOVER.md](../HANDOVER.md) and
  [../ops/cms-runbook.md](../ops/cms-runbook.md) must say where they are. A backup nobody
  can find is not a backup.

GitHub disables scheduled workflows after 60 days of repository inactivity. Only commits
reset the timer, and this workflow commits weekly, so it most likely sustains itself. Do
not rely on that reasoning — the runbook carries a liveness check instead, because a backup
that stopped silently is worse than no backup at all.

**Cadence: weekly, plus a manual trigger.** Content changes a few times a month, so a daily
export would commit near-identical dumps some 365 times a year and bury the one revision
you eventually need in noise. Weekly bounds the worst case at six days of lost editing, and
weekly commits reset GitHub's 60-day timer with room to spare.

The workflow also carries `workflow_dispatch`, so anyone can take a snapshot by hand before
a content-model migration, a Strapi upgrade, or a heavy editing session. The schedule is the
safety net for the days nobody is thinking about backups; the manual trigger is what you
use on the day you already know you are about to do something risky.

**Rule 3 — Split the content at the entity level, never at the field level.**

| Location | Entities |
| --- | --- |
| **Git** (MDX/JSON, dev-edited through PRs) | Mission, Timeline Entry |
| **Strapi** (editor-facing) | Stellar Talk, Nebula Night, Galactic Summit, Schedule Event, Announcement/News, Alumni, Sponsor |

The rule as stated to a new member: **missions and the timeline live in the repository;
everything else lives in Strapi.** The boundary must be sayable in one sentence, because
it has to survive people who were not present when it was drawn.

A Mission is **not** split across both systems. Splitting it at field level would spare
perhaps one PR per year and would cost every future editor an inexplicable half-empty
record. Missions are the credibility content, they stop changing once a mission ends, and
an error in a stated apogee is what a judge notices. Keep the whole entity in git.

### 3. Git-resident content layout

One directory per entity:

```
content/missions/apogee-1/
├── index.json     # locale-independent facts: dates, apogee, status, patch, links
├── en.mdx         # English prose + English slug in frontmatter
└── tr.mdx         # Turkish prose + Turkish slug in frontmatter
```

Facts live once. A launch date and an apogee in metres are not translations of each other,
and duplicating them into both locale files guarantees they diverge.

Slugs are the exception, and they go in the locale files rather than in `index.json`.
Because [../../design/i18n.md](../../design/i18n.md) uses fully localized URL segments, a
slug is locale-dependent by definition — it is neither a shared fact nor prose. A missing
Turkish slug is a broken route rather than a missing translation, so
[0004-verification.md](0004-verification.md) asserts both slugs exist, not merely both
files.

Timeline Entry uses the identical layout, so the parity check is one rule covering all git
content rather than one rule per entity type.

### 4. Hosting: Strapi on Render Starter, Postgres on Neon free tier

Roughly $7/month total. The Next.js frontend is on Vercel — see
[0001-stack.md](0001-stack.md).

- **Strapi cannot run on Vercel.** Serverless has no persistent process, no WebSocket
  support, and the admin panel degrades or fails outright. Frontend on Vercel, CMS on
  Render. Do not attempt to co-locate them; this is a recurring suggestion and the answer
  is always no.
- **Do not use Render's free Postgres.** Free databases are capped and are deleted a fixed
  period after creation. Use Neon's free tier, which is permanent and includes connection
  pooling.
- **Verify the build fits in 512 MB before committing to Starter.** Strapi's admin-panel
  build is the memory-hungry step, and out-of-memory during build is the most common
  Strapi deployment failure. If it fails, build the admin in CI and deploy the artifact
  rather than jumping to a larger instance — the failure is a build-time memory spike, not
  a runtime requirement, so paying for a bigger instance year-round is the wrong fix.

**Render over a DigitalOcean droplet, on operational legibility rather than price.** A
droplet means somebody owns SSH, systemd, nginx, certbot renewals, OS patching and
backups. That knowledge leaves when that person graduates, and the site degrades silently
over the following year. Git-push deploys and a dashboard survive turnover.

**Strapi Cloud explicitly not wanted.** It sells uptime, and rule 1 removed our uptime
requirement. Paying for the one property we engineered away is the wrong trade.

### 5. Media: Cloudflare R2, with transformation at the edge

Uploads must **never** be written to the Strapi instance's local filesystem. Render's disk
is ephemeral, so uploads vanish on redeploy — and even with a persistent disk attached,
serving images from Strapi means Strapi going down takes every photograph offline, which
violates rule 1 outright. On a photography-led site, broken images are indistinguishable
from a broken site.

**Cloudflare R2 via Strapi's S3-compatible upload provider**
(`@strapi/provider-upload-aws-s3`). R2 charges no egress, which matters when the best
content is multi-megabyte launch photography.

Two configuration details that are the usual cause of a failed first attempt:

- **R2 does not support ACLs.** The `ACL` parameter must be omitted from `params`
  entirely. Setting it — as almost every S3 example on the internet does — fails.
- `region: 'auto'`, with `endpoint` of the form
  `https://<account-id>.r2.cloudflarestorage.com`.

**A custom domain is bound to the bucket** at `media.<DOMAIN>`. The default `r2.dev` URL
is rate-limited and explicitly not intended for production traffic. This makes domain
registration a prerequisite for media working at all, not merely for pretty URLs — see
[../ops/cms-runbook.md](../ops/cms-runbook.md), step 1.

**Image resizing happens at Cloudflare's edge, in front of R2.** Verified 2026-08-15: for
images stored outside Cloudflare Images — which is our case, since originals live in R2 —
the first 5,000 unique transformations per month are free, then $0.50 per 1,000, and
transformations **no longer require a paid plan**. Combined with R2's zero egress, this
site's expected volume sits inside the free allowance.

The alternative considered and rejected was pushing everything through `next/image` on
Vercel. A photography-heavy site can exhaust Vercel's free transformation quota, and the
failure mode is that **every image on the site stops being optimised at once** — a
site-wide visual regression triggered by traffic rather than by a deploy. Moving
transformation to the same provider that stores the originals removes the coupling
entirely.

### 6. Media backup: R2 is a CDN, not a system of record

**Decision: media is not backed up by this project.** Losing the bucket costs re-upload
effort, not data.

This is only true if the originals genuinely live somewhere durable. The project brief's
suggestion of "a bucket lifecycle rule or a periodic copy" conflates two different things
— a lifecycle rule is a retention policy, not a backup — and neither is worth building if
the photographs already exist in a media archive the team maintains anyway.

**The system of record is the KUASAR media archive on a Google Shared Drive**, in the club
Google Workspace account. A *Shared Drive* specifically, never a folder in an individual's
*My Drive*: My Drive files are owned by the account that created them and leave with it when
that account is closed, which is exactly the failure this whole ADR is arranged around.
Shared Drive files are owned by the organisation, so a member graduating does not take the
archive with them.

**R2 has no object versioning, and cannot be made to.** Cloudflare lists
`GetBucketVersioning` and `PutBucketVersioning` as unimplemented and offers no
`ListObjectVersions` at all; R2's lifecycle rules delete and transition objects by age,
which is retention, not history. So there is no in-R2 protection against an editor
overwriting an asset, and the durable copy has to live off-provider. Recorded here
explicitly so nobody spends an afternoon looking for the setting.

Drive is a system of record, not an immutable one. A folder can be deleted there too;
Drive's trash holds deleted items for 30 days, which is a genuine recovery window and not
immunity. So the obligation stays in the runbook rather than moving into code:
[../ops/cms-runbook.md](../ops/cms-runbook.md) requires re-verifying **annually** that the
Shared Drive still exists, still has a named owner, and still holds the originals. If that
verification ever fails, this decision is void and an off-provider copy of the bucket
becomes necessary.

Media in git remains forbidden. It would make the repository unusable within two seasons.

### 7. Galactic Summit theming: the one sanctioned CMS-to-design coupling

Galactic Summit may carry its own brand feel per year, bounded. Per-year variation is
limited to **constrained enum fields on the Strapi entity** — an accent selected from a
fixed set, a hero treatment selected from a fixed set, and one background image upload.

The enum's permitted values are defined in code and documented in
[../../design/tokens.md](../../design/tokens.md). So:

- Choosing among existing options is a **data operation**. Adding the 2028 edition
  requires no code change, satisfying rule 5 of [0001-stack.md](0001-stack.md).
- Adding a **new** option is a **code change**, because it means adding a token.

Never new components, never a new layout. Unbounded, this clause forks the codebase by the
third year: each Summit gets "just one small exception" until there are four parallel
implementations and nobody dares delete any of them.

This is the only place where a CMS field selects a design token, and it is recorded here
precisely so that the next request to do it somewhere else has to argue against a written
boundary rather than against a vague preference.

### 8. Editor preview: Strapi's native preview into Next.js Draft Mode

Editors get a preview. Without one, the combination of static generation and
webhook-driven revalidation means publishing blind, which produces the worse workflow of
publishing to check and then unpublishing.

Strapi's `admin.preview` config points at a `/api/preview` route handler in `apps/web`
that validates a shared secret and enables Draft Mode. This is a **bounded exception** to
"user-facing routes never fetch Strapi in the request path": the exception is the preview
route only, it requires the secret, and it must carry `noindex`.

Three implementation notes, each one a known way this breaks:

- **Strapi's published example calls `draftMode()` without awaiting it.** That is the
  pre-Next-15 API. On Next 15+ it is `const draft = await draftMode()`. Copying their
  sample verbatim is the obvious failure and it fails confusingly.
- Strapi renders the frontend **inside an iframe** in the admin panel, so `apps/web` must
  permit framing from the Strapi origin. Scope the `frame-ancestors` exception to the
  preview route; do not weaken it site-wide.
- Strapi's `preview.config.allowedOrigins` must list the frontend URL, and the handler
  redirects to a pathname the handler itself derives — never to a URL taken from a query
  parameter, which would be an open redirect.

### 9. Account ownership

The KUASAR club account owns Render, Neon, Cloudflare, Vercel, GitHub and the Google
Workspace account that holds the media Shared Drive and the forms. **Never a member's
personal card.** At least two people set each account up together, and every account
appears in [../HANDOVER.md](../HANDOVER.md) with its owner and its renewal date.

Google Workspace is load-bearing rather than incidental: decision 6 makes its Shared Drive
the system of record for all original photography, so it is not merely where the Join Us
form lives.

Do not plan around trial credits. They expire in weeks and bind to one individual's
identity, which is the precise failure this arrangement exists to prevent.

## Known debt: KVKK

The privacy notice, form data handling and the overall KVKK position are deferred. They
are recorded here as **debt with a named holder**, not as a resolved question. Until it is
resolved:

- **NEVER add third-party analytics, embeds, pixels or tag managers.**
- Join Us, Connect Us and the Summit registration CTA are **links** to Google Forms hosted
  in the club Google account. Linking is permitted; **embedding a form in an iframe is
  not** — an embed is a third-party script under the rule above, a link is navigation.
  Member applications must not land in a personal Drive.

**One part of this is not deferred.** Alumni records carry a photograph and a LinkedIn
URL — see [../../design/content-model.md](../../design/content-model.md). That is personal
data about people who have left and cannot easily be re-consented. The consent requirement
is therefore made **structural rather than procedural**: the Alumni content type carries a
required consent field, so an editor physically cannot publish a portrait without
recording where consent came from.

A policy in a document nobody reads does not survive turnover. A required field does.

**The snapshots make this sharper, and not for the obvious reason.**
[0005-repository-visibility.md](0005-repository-visibility.md) makes this repository public,
and rule 2 commits Strapi's content into it.

Start by ruling out the argument that sounds right and is not. **Published content being in
a public repository is not an exposure.** An alumnus's name, photograph and LinkedIn URL are
on the website deliberately; putting the same fields in a dump hands the world nothing it
could not read off `/alumni` already. Anyone re-reading this section will reach for that
objection, so it is answered here rather than left to be rediscovered.

The real difference is **permanence**. A website supports erasure and git does not:

| | Live site | Snapshot in git |
| --- | --- | --- |
| Alumnus asks to be removed | Unpublish; gone within one revalidation | Still in every dump ever committed |
| Fixing it | — | Rewrite history, which does not work once anyone has cloned or forked |

This is a *snapshot* problem rather than a *public* problem — it exists on a private
repository too. What visibility changes is whether it is recoverable: privately you can
force-push and know the five clones you have to chase, publicly you cannot. So making the
repository public converts an awkward cleanup into an obligation this project cannot honour.

Three requirements follow, and none is optional:

- **Alumni are excluded from the export entirely.** Not the consent fields — the whole
  entity. This is rule 3 of decision 2 applied to backups: excluding one field would leave
  an inexplicable half-empty record for whoever restores it, and field-level splits are
  exactly what this ADR forbids elsewhere and for the same reason. With the entity out, the
  consent fields are out as a consequence rather than as a second rule to remember.
- **The export is restricted to published entries.** Drafts are not on the website, so
  unlike published content they *would* be a genuine new exposure — a half-written
  announcement or an unreleased Summit detail, public permanently. Verify on the first run,
  before visibility is flipped.
- **Neither rule may be relaxed to make a restore easier.** If a restore is painful because
  Alumni are missing, that is the design working. See Consequences.

What this buys: an erasure request is honoured by unpublishing in Strapi, and it is actually
honoured, because there is no second copy in a public branch quietly contradicting it.

## Consequences

- Editing requires Strapi to be up. That is the accepted cost, and it is bounded to
  editing rather than to viewing.
- Deploys require Strapi to be up. That is the unbounded cost, recorded in
  [0001-stack.md](0001-stack.md) rather than hidden here.
- The snapshot branch is invisible from a normal clone, so its discoverability depends
  entirely on the handover documents being read. This is the weakest link in the backup
  story and is deliberately called out rather than smoothed over.
- **Alumni are the one entity with no backup at all.** If the Neon database is lost, alumni
  records go with it and no dump will bring them back. This is the price of the exclusion
  above and it is paid deliberately.

  It is affordable because Alumni is also the cheapest entity to rebuild: some tens of
  records of name, years, sub-team and role, all of which the club holds in its own
  membership records regardless, and the portraits are already in the media Shared Drive
  named in decision 6. Losing it costs an afternoon of data entry, not knowledge.

  **The exception is the consent evidence,** and it is worth naming because it is the one
  part that cannot be reconstructed by asking around. `consentSource` and `consentRecordedAt`
  are records *of a past event*. Re-creating them means re-contacting people who have already
  left — which is precisely what
  [../../design/content-model.md](../../design/content-model.md) says cannot easily be done.
  In practice the correct response to losing them is to take the affected portraits down
  until consent is obtained again, which is the right answer under KVKK and an unwelcome one
  operationally.

  If that trade ever looks too expensive, the mitigation is an Alumni export kept in the
  club Google Workspace beside the media archive: access-controlled, honours deletion, and
  adds no account to the handover because that Drive already exists with a named owner and an
  annual check. It is deliberately **not** required here, because a manual annual export is
  exactly the kind of process that dies with the person who ran it — and a backup everyone
  believes in but nobody performs is worse than a documented gap.
- Two content workflows exist permanently: PRs for missions and the timeline, the admin
  panel for everything else. New contributors will ask which one applies. The one-sentence
  rule in decision 2 is the answer, and it should be quoted verbatim rather than
  paraphrased, because every paraphrase drifts toward field-level splitting.

## Alternatives considered

**Everything in git, no CMS.** Simplest possible handover, zero running cost, perfect
history. Rejected on the founding constraint: non-technical members must edit without
GitHub accounts.

**Everything in Strapi, no git content.** One workflow to explain. Rejected because
missions are the credibility content and belong under review, and because a database is a
worse home than git for facts that stop changing.

**Strapi Cloud.** Removes the ops burden entirely. Rejected in decision 4: it sells uptime,
which rule 1 already made unnecessary.

**Media on Vercel via `next/image`.** One fewer provider. Rejected in decision 5: quota
exhaustion is a site-wide, traffic-triggered visual regression.

**Off-provider media backup.** Genuinely safer. Rejected in decision 6 as work that
duplicates a media archive the team already maintains — conditional on the runbook
verifying that archive actually exists.
