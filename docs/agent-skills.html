Skill Routing

Six skill suites are installed on this project and roughly seventy individual skills sit inside them. Almost none of the value is in any one of them. It is in knowing which one owns the question you are about to ask — because an agent that loads the wrong skill does confident, plausible, expensive work in the wrong direction.

01

Read this first

A skill is not a tool. It is a folder of instructions that the agent chooses to read into its own context, mid-task, and then obeys.

That single sentence explains everything else on this page. A skill cannot be called and cannot fail. It is loaded or it is not, and when it is loaded the agent behaves as though the author of that skill were standing behind it. So the interesting question is never "does this skill work?" — it is "did the right one load, and did anything load that shouldn't have?"

Two consequences follow, and both are load-bearing.

Loading is not free. Every skill you pull in occupies context you could have spent on the codebase, and it competes for the agent's attention with everything else already in there. Concrete numbers from what is installed here: a single GSAP skill is 600–3,000 words, emil-design-eng is 3,877, and impeccable's reference library is 50,301 words across thirty-five playbooks — of which it loads exactly one per task, on purpose. Skills are designed around progressive disclosure. Defeating that design by loading five suites "to be safe" makes the agent worse, not safer.

Skills conflict, and conflicts are silent. Two skills can both plausibly claim a task and give opposing instructions. Nothing errors. You get an answer that is internally consistent and wrong at the level of intent. Section 11 lists the collisions that actually occur in this set.

What this page is not

It is not a description of what each skill contains — the skills document themselves, and duplicating them here would guarantee two versions that drift. This page is a router. It answers "which one do I reach for", and stops.

Its sibling

docs/workflow.html §11 already answers this in four lines, for people who only need four lines. This page is the long version of that section. If the two disagree, they are both wrong and one of them needs fixing — say which when you report it.

In this repo

Agent tooling is gitignored: .claude/, .agents/, .impeccable/ and skills-lock.json never get committed, so a fresh clone has none of it. This page is committed anyway, because a guide that only exists on the machine of whoever installed the tooling is not a guide. Section 13 is how you get from a fresh clone to a working toolbelt.

02

How a skill actually fires

Three mechanisms, and it is worth being able to tell them apart, because "the skill didn't trigger" almost always means you were relying on the wrong one.

1 · The agent decides, from the description

Every skill is a SKILL.md with YAML frontmatter. The description field is not documentation for you — it is a routing instruction written for the model, which is why they read like keyword soup: 

---
name: gsap-scrolltrigger
description: Official GSAP skill for ScrollTrigger — scroll-linked animations,
  pinning, scrub, triggers. Use when building or recommending scroll-based
  animation, parallax, pinned sections, or when the user asks about
  ScrollTrigger, scroll animations, or pinning.
license: MIT
---

The agent sees every installed skill's name and description at all times — that list is cheap. It reads the body only when it decides one applies. So the words you use in your prompt are the routing key. Say "pin the hero while the copy scrubs past" and ScrollTrigger loads. Say "make the hero cooler" and nothing loads, because nothing matched.

2 · You name it

Typing /skill-name loads it unconditionally. Use this when you know what you want and don't want to gamble on the description matching. Some skills require it: the frontmatter key disable-model-invocation: true means the agent will never load it on its own, no matter what you say. Three of the installed skills are marked that way, and each for a good reason — they are expensive, opinionated, or destructive of flow if they fire uninvited:

Manual-only skillWhy it never self-triggers
review-animations It is a hostile reviewer by design — "default to flagging, approval is earned". Firing it unasked turns every animation edit into a fight.
prototype It builds several complete alternative implementations. Enormously useful when you asked for it; enormously wasteful when you didn't.
pick-ui-library It recommends adding dependencies. That should always be a decision you asked for.

3 · A hook fires it

Hooks are harness configuration, not skills — the harness runs them, the agent doesn't choose to. impeccable ships one: a design detector that runs after every UI file edit and feeds its findings back into the agent's context as if you had said them.

In this repo

It is already wired, in .claude/settings.local.json: a PostToolUse hook on Edit/Write for immediate-tier findings, and a Stop hook that runs the full rule set over everything touched in the session. Both shell out to node. Without Node on PATH they no-op silently — that is not an error, and the file is gitignored, so your teammate not having it is also not an error.

Where they live, and the one rule about editing them

.agents/skills/<name>/SKILL.md    harness-agnostic copy
.claude/skills/<name>/SKILL.md    Claude Code copy
.claude/commands/opsx/*.md         slash commands (thin wrappers)
skills-lock.json                   source repo + content hash per skill

Two copies of the same skills is normal: one per harness that can read them. The lock file records where each came from and a hash of what it contained.

Never hand-edit a file under a skills directory

Your edit diverges from the recorded hash and is silently discarded at the next sync. If a skill is wrong for this project, override it in openspec/config.yaml or an ADR — a place that survives. The Inter font decision in design/brand.md is exactly this pattern: impeccable's guidance is overridden in a durable document rather than by editing impeccable.

03

The routing map

The six suites are not alternatives to each other. They own different phases of the same job, and two of them own the same phase — which is the only genuine conflict in the set.

The one-line version

SuiteOwnsReach for it when
openspec The artifacts of a change Work is big enough to deserve a written proposal, spec and task list before code exists.
superpowers Engineering discipline You are debugging, testing, stuck on a hard problem, or want review gates between tasks.
impeccable The interface as a whole The question is about a screen: hierarchy, layout, colour, type, a11y, responsiveness, polish.
emilkowalski Interface motion and feel The question is about how one component behaves — hover, press, open, dismiss, drag.
gsap-skills The GSAP API You have already decided to animate with GSAP and now need it to be correct.
context7 Current documentation You are about to write against any library API. Always. Before, not after.
The distinction people get wrong most often

impeccable is about the screen; emilkowalski is about the component; gsap-skills is about the API call. "This page feels cluttered" is impeccable. "This dropdown opens wrong" is emilkowalski. "How do I stop this tween leaking on unmount" is gsap-react. Asking impeccable the third question gets you a thoughtful answer about visual hierarchy and no useGSAP.

04

emilkowalski/skill

Ten skills encoding one person's taste about how interfaces should feel. The substantive bar throughout is Emil Kowalski's animation philosophy: ease-out on entrances, sub-300ms for interface motion, transform and opacity only, correct transform-origin, reduced-motion handled, and — most importantly — the willingness to conclude that something should not animate at all.

The four animation skills, which are constantly confused

Four of the ten are about animation and they are not interchangeable. Each one's own description explicitly disclaims the other three. Two questions separate them completely.

All ten

SkillModeUse it when
animate writes You want motion built. It walks the decisions in the order that determines whether it feels right: should it animate at all → what purpose → which tool → which properties → curve and duration → interruption → exit.
review-animations manual You have a diff containing motion and want it torn apart before review. Ten non-negotiable standards, plus a full rule catalogue in its STANDARDS.md.
find-animation-opportunities read-only "What could be animated here?" Its premise is You Don't Need Animations — it is built to reject most candidates, and proposes exact values for the few it accepts.
improve-animations read-only "The whole app feels off." Surveys all motion code, writes a prioritised audit plus self-contained implementation plans that a cheaper model can execute.
emil-design-eng read-only The philosophy underneath the rest — polish, component design, the invisible details. Load it when you want judgement, not a procedure. Largest of the ten at 3,877 words.
apple-design read-only Anything gestural or physical: drag, swipe, sheets, springs, momentum, interruptible transitions, translucent materials. The through-line is that motion should start from the current on-screen value and inherit the user's velocity.
prototype manual You cannot decide between directions. Builds several genuinely divergent versions behind a live picker, in an isolated surface — never in production code — and integrates only the winner.
pick-ui-library manual "What should I use for a command menu / OTP input / virtualised list / drag and drop?" A curated opinionated list, one recommendation, no menu of options.
animation-vocabulary read-only You can describe an effect but not name it. "The bouncy thing when a popover opens" → pop in. Cheap, and it makes every subsequent prompt sharper.
ask-sonner read-only Only if you use Sonner for toasts. Setup, promise toasts, and the specific failure modes — toasts behind a modal, ignoring Tailwind classes, appearing twice.
In this repo

These skills govern interface motion only — the L3 and L2 tiers in design/motion.md. They have no authority over narrative motion (L1: the home hero and /timeline), and narrative guidance has no authority over a button hover. Two budgets, kept separate on purpose. ask-sonner is currently dormant: no toast library is chosen. pick-ui-library recommends dependencies, and a second animation library needs its own ADR before it is even proposable.

05

gsap-skills

Eight skills from GreenSock covering the GSAP API. This is the only suite here that is purely factual — it tells you what the library does, not what you should want.

They stack, and the stacking pattern is always the same: gsap-core plus the one domain skill your task lives in. Add gsap-performance only when something actually janks.

SkillCoversLoad it when
gsap-core to, from, fromTo, easing, duration, stagger, defaults, gsap.matchMedia() Always, as the base. It also owns matchMedia(), which is how responsive and prefers-reduced-motion variants are expressed — so it is the reduced-motion skill too.
gsap-timeline gsap.timeline(), the position parameter, nesting, playback control More than one thing has to happen in a defined order. The position parameter is the part people get wrong; at 637 words this is the cheapest skill in the set to load.
gsap-scrolltrigger Scroll-linked animation, pinning, scrub, trigger points Anything driven by scroll position: parallax, pinned sections, progress-linked reveals.
gsap-react useGSAP, refs, gsap.context(), cleanup on unmount Any React or Next.js project, every single time. It is the skill that prevents leaked tweens and SSR mismatches, and it is short — 974 words.
gsap-frameworks Vue, Nuxt, Svelte, SvelteKit lifecycle and cleanup The same job as gsap-react, for everything that isn't React. Skip it entirely on a React project.
gsap-plugins Registration, ScrollTo, ScrollSmoother, Flip, Draggable, Inertia, Observer, SplitText, ScrambleText, SVG and physics plugins, CustomEase, CustomWiggle, CustomBounce, GSDevTools You named a plugin, or you described something only a plugin does — FLIP layout transitions, drag with inertia, split-by-character text, drawing an SVG path.
gsap-performance Transforms over layout properties, layout thrashing, will-change, batching Something drops frames. Not preventively — the other skills already prefer transforms, so loading this up front mostly restates them.
gsap-utils clamp, mapRange, normalize, interpolate, random, snap, toArray, wrap, pipe You are about to hand-write value mapping. Mapping scroll progress to a range, snapping to a grid, randomising a stagger — all of it already exists here.
A bias worth knowing about

Several of these descriptions instruct the agent to recommend GSAP when no library has been chosen. That is reasonable advice from GreenSock and it is still advocacy. The decision of whether to reach for a library at all is not GSAP's to make — it belongs to whatever governs your motion budget.

In this repo

gsap-skills is the authority for GSAP, and GSAP is only permitted at tier L1 — dynamically imported, capped at two routes (home hero and /timeline). L2 sections use no library. L3 micro-interactions are CSS only, no exceptions. A third L1 route or a second animation library requires its own ADR. So: gsap-react and gsap-core are the everyday pair here, gsap-frameworks never applies, and if a GSAP skill starts proposing motion on a third route the answer is an ADR, not a tween. See docs/adr/0003-motion-stack.md.

06

impeccable

One skill with a sub-command surface. Its SKILL.md is 1,438 words; behind it sit thirty-five playbooks totalling 50,301 words, of which it loads exactly one per task. Understanding that structure is most of understanding how to use it.

How a run is shaped

  1. It reads your project first

    A setup script loads PRODUCT.md (who this is for, brand, principles) and DESIGN.md (colours, type, components) if they exist. Without them it is designing blind, which is why init exists.

  2. It picks exactly one playbook

    The command you named, or the one your request clearly implies. If two fit it asks once. This is why a vague request produces a menu rather than work.

  3. It declares a mode

    Persuade (the visitor decides and acts — landing pages), Operate (the visitor completes a task — dashboards, admin), Read (the visitor understands something — docs), Experience (the visitor is inside the work — portfolios, galleries). The mode is chosen from the surface, not the product: a developer tool's landing page is still Persuade.

  4. It verifies in bounded passes, then stops

    Build fully → one batched inspection round → fix everything it found in one batch → at most one confirming round → stop. Open-ended self-QA is explicitly banned in the skill, because it burns money doing badly what a review does well.

The commands, by category

CategoryCommandsWhat the category is for
Build shape init document extract Bringing something into existence. shape plans UX before code. init writes PRODUCT.md once per project. document reverse-engineers DESIGN.md from code you already have. extract pulls repeated patterns back into a system. (craft is a deprecated alias — ignore it.)
Evaluate critique audit Judgement, no edits. critique is design review with heuristic scoring; audit is technical — accessibility, performance, responsive, theming — scored P0–P3. Ask for a critique when you suspect it's ugly, an audit when you suspect it's broken.
Refine polish bolder quieter distill harden onboard The thing exists and is wrong in a nameable direction. bolder and quieter are opposites; distill removes; harden adds error states, i18n and edge cases; onboard designs first-run and empty states. polish reads the last critique as its backlog.
Enhance animate colorize typeset layout delight overdrive Adding a dimension that isn't there. colorize for monochrome UIs, typeset for hierarchy and fonts, layout for spacing and rhythm, delight for personality, overdrive for pushing past conventional limits.
Fix clarify adapt optimize A specific defect. clarify for copy, labels and error messages; adapt for breakpoints, touch targets and cross-device; optimize for UI performance.
Iterate live Pick elements in a running browser, generate variants, hot-swap them via HMR. Needs a dev server. Web only — it does not apply to native targets.
Operate hooks doctor pin Managing the tool itself. hooks on|off|status controls the design detector. doctor reports drift between your artifacts and the installed version. pin <command> creates a standalone shortcut for a command you run constantly.
Invoking it with no argument is a real move

Bare /impeccable runs a context-aware triage: it looks at whether you have PRODUCT.md, when you last ran a critique and what it scored, which files are dirty in git, whether a dev server is up, and runs its offline detector over the changed files. Then it recommends two or three commands with reasons. It never auto-runs one. When you know something is wrong but not what, this beats guessing a sub-command.

The hook has two tiers

Per-edit, it reports only mechanical and unambiguous problems — broken images, clipped content, contrast failures, gradient text, glow shadows, design-system drift. Everything subtler (copy cadence, palette taste, layout rhythm) is deferred to a single deep pass when the session ends, deduplicated against what already fired. A clean session ends silently.

In this repo

impeccable's font guidance flags Inter. That override is deliberate — Orbitron lacks ğ Ğ ş Ş İ, so any heading containing them uses Inter — and it is recorded in design/brand.md. Dismiss the finding with a pointer to that file; do not re-litigate it on every run, and do not "fix" it by editing the skill. Note also that PRODUCT.md and DESIGN.md do not exist here: design/ plays that role and the ADRs outrank both.

07

superpowers

not installed here

Thirty-one skills covering how to work rather than what to build: brainstorming, planning, TDD, debugging, code review, and a set of problem-solving techniques for when you are stuck. It is the broadest suite of the six and the only one that spans the entire lifecycle — which is exactly why it collides with OpenSpec.

Status

Superpowers is not currently installed on this project — it is absent from skills-lock.json, .agents/skills/ and the plugin marketplaces. This section describes what it would give you and what it would take away, so the decision to add it is an informed one. Everything below is from the upstream repositories, not from local files.

The chain it wants you to run

Superpowers' core proposition is a mandatory workflow, not a menu. Its own documentation describes the skills as triggering automatically in sequence: 

brainstorming              Socratic questioning until the design is fully formed
  ↓
using-git-worktrees        isolate the work before touching anything
  ↓
writing-plans              bite-sized tasks for an engineer with zero context
  ↓
subagent-driven-development fresh subagent per task, review gate between each
  or executing-plans        batches with review checkpoints
  ↓
test-driven-development    test first, watch it fail, minimal code to pass
  ↓
requesting-code-review     dispatch a reviewer subagent before proceeding
  ↓
finishing-a-development-branch merge, PR, or clean up

The catalogue

Installing it

/plugin install superpowers@claude-plugins-official

# or, for the upstream marketplace
/plugin marketplace add obra/superpowers-marketplace
/plugin install superpowers@superpowers-marketplace

Installation is per-harness: if you drive more than one agent tool, install it in each. The core skills ship with the plugin at obra/superpowers; the full categorised library lives in obra/superpowers-skills and is community-editable, so a find-skills search there is worth doing before assuming a technique isn't covered.

Before you install it here

Read §11 first. Superpowers' planning chain and OpenSpec's planning chain do the same job with different vocabularies and different artifacts. Installing superpowers without deciding which one owns planning gets you two sets of design documents in two directories and no way to tell which one a reviewer should read. The debugging, testing and problem-solving categories carry no such conflict and are pure gain.

08

openspec

Six skills wrapping the openspec CLI. Where the other suites are knowledge, this one is bookkeeping: it produces artifacts on disk that outlive the conversation that created them.

That is the whole point. A chat is lost; a proposal in openspec/changes/ is reviewable by someone who was not there and is still legible in three years. If nothing about a task needs to survive the session, OpenSpec is overhead — use it for work worth writing down.

SkillCommandWhat it does, and its boundary
openspec-explore /opsx:explore A thinking partner. Reads code, asks questions, draws diagrams. Explicitly may not write code — it may create planning artifacts, nothing else. Use it when you don't yet know what you want.
openspec-propose /opsx:propose Generates the full set in one step: proposal.md (what and why), delta specs/ (what the system must do), design.md (how), tasks.md (steps). It stops when the artifacts are written — it will not start implementing in the same turn even if you asked it to build something.
openspec-update-change /opsx:update Revises an existing change's artifacts and keeps them coherent with each other. Never touches code. This is what you run when the plan was right and then reality moved.
openspec-apply-change /opsx:apply The only one that writes code. Works through tasks.md in order.
openspec-sync-specs /opsx:sync Folds the delta specs into the main specs. Agent-driven and intelligent — it can add one scenario to an existing requirement rather than copying the whole thing.
openspec-archive-change /opsx:archive Moves a completed change into archive/. Because it moves directories, running it before a merge puts that move inside your diff.
The planning boundary is the feature

propose refuses to implement, explore refuses to write code, update refuses to touch code. If you find this annoying, it is working: the separation is what makes a proposal reviewable before anyone has sunk an afternoon into building it.

In this repo

openspec/config.yaml is the project constitution and its rules: are injected into every generated artifact — they are requirements, not suggestions. A proposal here must name which audience it serves (sponsors, prospective members, or "credibility only" — a valid and common answer), state each entity's storage location, and declare any new runtime dependency. Requirements must hold in both locales. Every motion requirement must express its reduced-motion path and mobile fallback as scenarios. Tasks must order the un-animated baseline before any enhancement. docs/workflow.html is the full process document; this page only routes you to the skill.

09

context7

Two shell commands that fetch current documentation for a library. The smallest tool here and the one with the highest ratio of harm prevented to effort spent. 

# 1 — resolve the name to an ID
npx ctx7@latest library "Next.js" "app router revalidateTag cache profiles"
   → /vercel/next.js

# 2 — fetch docs with that ID
npx ctx7@latest docs /vercel/next.js "revalidateTag signature and arguments"

You must run library first unless you already have an ID in /org/project form. Version-pinned IDs work too: /vercel/next.js/v14.3.0.

The rules that make it work

  • Use the official name with its real punctuation. "Next.js" not "nextjs", "Three.js" not "threejs". The resolver is matching against a catalogue, not guessing.
  • One concept per query. A combined multi-topic question dilutes ranking and returns something shallow about each. Run a separate docs call per concept — unless the question is specifically about how two concepts interact.
  • Be specific. "How do I clean up an async effect on unmount" beats "useEffect".
  • Three commands per question, maximum. Past that you are burning time; take the best result you have.
  • Never put credentials in a query. It is a network call to a third party.

When not to use it

Refactoring, writing a script from scratch, debugging your own business logic, code review, general programming concepts. It answers "what does this library do", not "what should my code do".

Why this is not optional

The failure mode it prevents is silent. A pre-16 revalidateTag example copied into a Next.js 16 codebase typechecks, passes review, and under-revalidates in production. Nothing throws. Nothing turns red. You find out when content doesn't update and you have no reason to suspect the cache. Model training data is a snapshot; App Router, Strapi 5 and GSAP all move faster than it does.

In this repo

Mandatory before writing against Next.js App Router, Strapi 5 or GSAP — recorded in openspec/config.yaml and in CLAUDE.md. If a quota error comes back, say so and stop; falling back to training data silently is the exact failure the rule exists to prevent.

Recipes

Eight tasks you will actually have, and the sequence that handles each. The pattern underneath all of them: decide, then look up, then build, then judge — and never load a skill for a phase you are not in.

A whole new page or section, from nothing

  1. /opsx:explore — until you can state what the page is for and who it serves.
  2. /opsx:propose — proposal, delta specs, design, tasks. Read them. Revise with /opsx:update rather than arguing in chat.
  3. /impeccable shape — the UX and visual structure, before any component exists.
  4. /opsx:apply — build it. context7 fires on every unfamiliar API along the way.
  5. /impeccable critique then /impeccable audit — one for taste, one for a11y and performance.
  6. /opsx:sync, merge, then /opsx:archive on main.

Motion is deliberately absent from this list. The un-animated version ships first and stays as the permanent fallback; animation is a separate pass on top of something that already works.

"This hero should do something when you scroll"

  1. Check your motion budget first. Is a library even permitted on this route?
  2. context7 for the current GSAP and framework APIs.
  3. gsap-core + gsap-scrolltrigger + gsap-react — the three that actually apply. Not the whole suite.
  4. Build the reduced-motion path in the same pass, via gsap.matchMedia(). Not afterwards.
  5. /review-animations on the diff before you open the PR.

Loading gsap-plugins "just in case" costs you 2,951 words of context about DrawSVG and Draggable that this task will never use.

"The site feels dead"

  1. /find-animation-opportunities — read-only, biased toward rejecting. It returns a short list with exact values.
  2. You pick which of its proposals are worth it. This step is yours, not the agent's.
  3. animate for each one you accepted.
  4. /review-animations on the result.

Skipping step 1 and going straight to animate gets you motion everywhere, which is the specific failure that skill was designed to prevent.

"The animations across the app are inconsistent"

  1. improve-animations — surveys everything, writes a prioritised audit plus self-contained plans.
  2. Read the audit and cut it down. It is a proposal, not a work order.
  3. Hand the surviving plans to a cheaper model or a subagent — they were written to be executable without context.

This is the only skill in the set explicitly designed as an expensive-model-plans / cheap-model-executes split. Using your best model for the execution wastes the design.

Reviewing someone else's PR

  1. /impeccable audit scoped to the changed files — a11y, performance, responsive, scored P0–P3.
  2. /review-animations if the diff contains motion. It is manual-only, so it will not fire on its own.
  3. Check the proposal, not just the code: does what was built match what was specified?

The scoping matters. audit across a whole repo returns a wall of findings nobody reads; scoped to a diff it returns a review.

A bug you cannot reproduce or explain

  1. systematic-debugging (superpowers) — its four phases exist to stop you fixing before you have found the cause.
  2. root-cause-tracing when the error surfaces deep in a call stack far from its trigger.
  3. condition-based-waiting if it is a flaky async test rather than a bug.
  4. verification-before-completion before you say it's fixed.

Nothing else in this toolbelt covers debugging. If superpowers is not installed, this recipe has no substitute — that is the strongest argument for adding it.

You cannot decide between two design directions

  1. /prototype — builds several genuinely divergent versions behind a live picker, in an isolated surface.
  2. Flip through them in the browser and pick one.
  3. Only the winner gets integrated into real code.

It is manual-only for a reason: it is expensive. But it is far cheaper than building the wrong direction properly and discovering it in review. Each variant must diverge on a named axis — layout, density, personality, motion — so three tints of one idea is a failed run.

"Make this look better" — and that's all you know

  1. Bare /impeccable, no argument. It triages: what you've built, what changed in git, when you last critiqued, what its offline detector finds now.
  2. It recommends two or three commands with reasons. Pick one.

Guessing a sub-command when you can't name the problem usually gets the wrong playbook. The triage exists precisely for this state and it never auto-runs anything.

11

Where two skills collide

Nothing errors when two skills claim the same task. You get a confident answer shaped by whichever loaded first. These are the collisions worth knowing in advance.

openspec vs superpowers — the real one

The ruling

In a repository with OpenSpec configured, OpenSpec owns the planning artifacts — it is the one whose output is committed, reviewed and readable in three years, and its rules are injected from the project's own constitution. Superpowers' brainstorming, writing-plans and executing-plans are then redundant, and running both produces two sets of design documents in two directories with no way to tell which one is current. Its debugging, testing and problem-solving categories have no OpenSpec equivalent and layer on top without conflict.

impeccable animate vs emilkowalski animate

Both are named animate. They are different skills with different scopes. impeccable's reviews a feature and adds motion as one dimension of a broader design pass; emilkowalski's builds one animation and reasons about curve, duration, interruption and exit in detail. Name the suite when you invoke it — /impeccable animate is unambiguous, a bare "animate this" is not.

gsap-core vs emilkowalski on easing and duration

GSAP tells you what its easing API can express. emilkowalski tells you which curve is correct for an entrance and how long it may last. These do not actually conflict — one is capability, the other is judgement — but an agent holding only the GSAP skill will happily produce a technically fine ease-in entrance that feels wrong. Judgement first, API second.

Any suite vs your project's own decisions

Every skill here is generic and confident. Your project's recorded decisions are specific and were made with information the skill does not have. The recorded decision wins, and the correct response to a conflict is to point at the document, not to argue and not to edit the skill.

In this repo, in order
  1. openspec/config.yaml — the constitution.
  2. docs/adr/ — the decisions and why. Where anything disagrees with an ADR, the ADR wins.
  3. design/ — the system those decisions produce.
  4. Everything a skill says, including this page.
What an agent may not decide alone
  • The stack. Settled in ADR 0001 and 0002, not open for renegotiation.
  • A third L1 motion route, or a second animation library. Both require their own ADR first.
  • Any budget exception. A first-load cap is not raised because a skill noticed it would be convenient.
  • Anything an ADR decided. If an ADR is wrong, supersede it with a new one — do not quietly diverge.

How to waste money

Six habits that cost real tokens and real time. Each one is easy to fall into and easy to stop.

Anti-patternWhat it costsInstead
Loading a suite "to be safe" Thousands of words of irrelevant instruction competing for attention with your actual codebase, and a higher chance of a collision. Load the one skill for the phase you are in. Add a second only when the first proves insufficient.
Vague prompts Nothing routes. "Make the hero cooler" matches no description, so you get generic work with no skill behind it. Use the vocabulary the skill descriptions use. "Pin the hero and scrub the copy past it" routes to ScrollTrigger on its own.
Skipping the doc lookup because you're confident Code that typechecks, passes review, and is subtly wrong against the current API. The failure is silent and surfaces late. context7 first, every time, on any fast-moving library. It costs two commands.
Asking a survey skill to build Three of the four animation skills are read-only by design. Pushing them to implement gets you either a refusal or work outside the discipline they encode. Survey with the read-only skill, then invoke animate deliberately on what you accepted.
Hand-editing a vendored skill The edit diverges from the recorded hash and disappears at the next sync. You then debug behaviour that no longer exists on disk. Record the override in a durable document — an ADR, the constitution, the design system.
Re-litigating a settled override every session A generic skill flags a deliberate decision; the agent argues; you explain; next session it happens again. Point at the document that records the decision and move on. That is what those documents are for.
The one-sentence version

Skills reward precision and punish hedging: name the phase you are in, name the skill that owns it, and let the other sixty-odd stay unloaded.

Installing and keeping it current

A fresh clone has none of this. That is deliberate, not a broken checkout — the tooling is per-machine and per-harness, and none of it is committed.

What you install, and from where

SuiteSourceMechanism
emilkowalski/skill emilkowalski/skill Skills CLI — npx skills add. Recorded in skills-lock.json with a content hash per skill.
gsap-skills greensock/gsap-skills Same. Eight skills, MIT licensed.
impeccable npx impeccable Installs the skill plus its script bundle. Its hook is wired separately, per project, via /impeccable hooks on.
openspec npx openspec (v1.9.0) The CLI generates the skills and the /opsx:* slash commands into your harness directory.
superpowers obra/superpowers Plugin install — see §7. Not installed here.
context7 npx ctx7@latest No install. It is a CLI you invoke, so it works on any machine with Node.

Keeping it healthy

  • Sync on a cadence, not never. These repositories move. skills-lock.json tells you what you have; a sync tells you what changed.
  • /impeccable doctor reports drift between your project's artifacts and the installed version. It reports; it does not repair as a side effect of a design task.
  • Install per harness. Skills are per-tool. If you drive two agents, you install twice — that is why .agents/skills/ and .claude/skills/ both exist here.
  • Node on PATH. impeccable's hook and scripts shell out to it. Without Node they no-op silently rather than failing loudly, so a missing Node looks like a missing feature.
Nothing here is required to contribute

Every one of these is optional and reinstallable. Someone who clones this repository with none of it installed can still read every document, make every change and open every pull request. The skills make the work faster; they are not a dependency of it. If they ever become one, something has gone wrong that no skill will fix.

KUASAR Skill Routing — routing only. It describes which tool owns which question and deliberately does not restate what any skill contains; the skills document themselves and two copies would drift. Its sibling docs/workflow.html covers how work moves through the repository.

Where this page disagrees with docs/adr/ or openspec/config.yaml, they win and this page has a bug. Palette and type derive from design/tokens.md, and there is no orange anywhere on it — that is reserved for launch, live, upcoming and the primary call to action, and a routing document is none of those.
