Air to Ground

Every Apollo flight produced an air-to-ground transcript: not a summary of what was decided, but a record of how the two sides actually talked. The value was never in any single exchange. It was in seeing the shape of a conversation that worked. This page is that, for driving an agent through the OpenSpec loop on this site.

01

Read this first

This page decides nothing. It shows what the process in docs/workflow.html looks like when a human and an agent are actually typing at each other.

Its two siblings are complete without it. docs/workflow.html tells you which command to run and in what order; docs/agent-skills.html tells you which skill owns which question. Both are correct and neither shows you a single sentence anyone said. That gap is the reason this page exists — the failure mode on this project is almost never not knowing the command. It is running the right command with a prompt that gave the agent nothing to work with, reading four generated documents too quickly, and discovering the problem in a diff.

The setting, stated up front so nothing here misleads you

Every transcript below is set after the scaffold exists — roughly after changes 1 to 4 of docs/workflow.html §08 have shipped, so apps/web is real, Tier A CI runs, locale routing works and the tokens are actual CSS.

None of that is true today. There is no package.json in this repository and nothing here runs. Not one command on this page can be pasted into a terminal this afternoon; every one of them is a command that will be correct on the day the scaffold lands. Writing the examples against today's empty repository was the alternative, and it would have made all fourteen sections about npm workspaces.

How to read a transcript

Three markers, used consistently. A line beginning ▸ is something the agent did — a command it ran, a file it read — rather than something it said. A box with a dashed border is a transcript kept as a warning. And an ellipsis on its own line means output was cut for length, never that something interesting was hidden.

What it says back — and, more importantly, what it asks.

Why it works

The lesson of that exchange, in one sentence. Every transcript has one.

Three things this page assumes you have accepted

  • The agent cannot see what you know. It cannot tell whether you have read ADR 0003 or whether you are about to violate it. Saying what you already know is not throat-clearing; it is half the prompt.
  • The artifacts are the memory, not the chat. A conversation is gone in a week. openspec/changes/<name>/ is readable by someone who was not there, which is the entire reason this repository uses OpenSpec at all.
  • Reviewing four short documents is cheaper than reviewing a thousand lines. If you skip the read-back, you have bought the ceremony and thrown away the thing it bought you.
In this repo

Where anything on this page disagrees with docs/adr/ or openspec/config.yaml, they win and this page has a bug — fix it, it is a tracked file. The constitution is already injected into every generated artifact, so a transcript that quotes a rule at the agent is demonstrating a waste, not a technique.

02

Anatomy of a prompt

Four parts. Drop any one of them and you can predict, in advance, exactly how the answer will be wrong.

The same request, twice

Costs a turn

You

build the timeline

Agent

Which timeline — the section on the home page, or the /timeline route? And should this include the scroll-linked sequence, or the baseline first?

… three more questions …

Why it fails

Not because the agent asked. Because you now answer four questions in sequence, and each answer arrives without the others.

Costs a sentence more

You

/opsx:propose timeline-baseline — the Timeline route at /[locale]/timeline, baseline only: no library, no scroll linking. Git content under content/timeline/, both locales, and it has to read correctly at zero and one entries. Tiers and budgets are in design/motion.md — point at it, don't restate it. Stop after the artifacts.

Agent

runs openspec new change "timeline-baseline"

One thing before I write the proposal…

Why it works

It still asks a question — but one, and a real one. Everything answerable from the repository has already been answered.

Point at documents. Never paste them.

The single highest-leverage habit on this project, and the one most people get backwards. Pasting design/motion.md into a prompt feels helpful and does three bad things: it spends context on something the agent can read in one tool call, it creates a second copy of a rule inside a transcript that nobody will ever update, and it invites the agent to treat your paste as the authority when the file has moved on. The path is the whole citation.

Say "budgets are in design/motion.md". Do not say "the budget is 120 KB first-load and 45 KB deferred" — you will be wrong about it within a year, and being confidently wrong at the agent is worse than saying nothing, because it will believe you.

Say what you already know, and how you know it

"I know /timeline is one of the two permitted L1 routes" does two things at once. It saves the round trip where the agent explains ADR 0003 back to you, and it makes your claim checkable — if you are wrong, the agent has a specific sentence to correct rather than a vague direction to nudge. A prompt that states no beliefs cannot be argued with, which sounds safe and is the opposite.

03

Walkthrough — planning the Timeline baseline

One change, start to finish, in two sections. This one ends with four documents and no code. §04 is where code appears.

The Timeline is the right example because it is the hardest thing on this site that is not the hero: git-resident content, both locales, a route with a localized segment, a direction that inverts reading-order expectation, and a motion tier that this change is deliberately not allowed to touch. Almost every trap in the repository shows up somewhere in it.

  1. Ask whether it is a change at all

    A new route with new observable behaviour. Yes. The threshold from docs/workflow.html §15 — if it changes observable behaviour or adds a dependency — is not close here, and §09 below covers the cases where it is.

  2. Think first — /opsx:explore

    Optional, and worth it exactly when you cannot yet state what you are building. Here, one thing is genuinely unresolved: the Timeline runs rightward from present to past, and design/motion.md requires that direction to be legible without motion — but does not say how.

    You

    /opsx:explore — I want to build the Timeline route. Before we propose anything: entries run rightward from present to past, and I don't know how to make that legible with no animation. What are the options, and what does the content model already give me to work with?

    Agent

    runs openspec list --json — no active changes

    reads openspec/config.yaml, design/motion.md, design/content-model.md, design/i18n.md

    Three affordances are available, and they are not exclusive:

      now                                          older
   │
   ▼
  ├──●─────────●───────────●──────────●──────▶
   2026        2025        2024       2022
   ↑           ↑
   axis label  "now" anchor        + an initial scroll nudge

    Two things the content model already decides for you. Entries carry a kind and an optional image, and the model says entries must read well without one — so the affordance cannot be carried by imagery. And at zero entries the section and its route are hidden.

    That last one has a consequence I want to check before we scope this. design/i18n.md keeps Timeline out of the navbar, so the only way a visitor reaches the route is the "view more" affordance on the home page's Timeline section. If zero entries hides the route, that affordance has to disappear too — which is a change to the home page. Is that in scope here, or does this change assume at least one entry exists?

    You

    In scope. The route hiding without the link hiding is a dead link, and I'd rather that live in one change than be discovered later.

    Agent

    Then the scope is the route, the direction affordance, and the home section's link visibility. Want me to capture this as a change?

    Why it works

    Explore earns its keep when it finds the question you did not know to ask. Two documents, read together, produced a dead-link bug that neither one contains — and it cost four sentences instead of a pull request.

    Explore mode may create artifacts if you ask it to. It may not write code, and if you ask it to it will tell you to leave explore mode first.

  3. Branch, then propose

    git switch -c change/timeline-baseline

    Branch first so the planning artifacts are versioned with the work from the very first commit. Then the prompt from §02, in full.

    You

    /opsx:propose timeline-baseline — the Timeline route at /[locale]/timeline, baseline only: no library, no scroll linking, that is a separate change. Git content under content/timeline/, both locales, correct at zero and one entries. Include hiding the home page's "view more" link when there are no entries. Tiers and budgets are in design/motion.md — point at it, don't restate it. Stop after the artifacts; I'll read them before we build anything.

    Agent

    runs openspec new change "timeline-baseline"

    runs openspec status --change "timeline-baseline" --json

    runs openspec instructions proposal --change "timeline-baseline" --json

    Created proposal.

    runs openspec instructions specs --change "timeline-baseline" --json

    Created specs at specs/timeline/spec.md.

    … design, then tasks, re-checking status between each …

    All four artifacts are written. The artifacts are ready for review. When you are ready, run /opsx:apply or ask me to apply this change.

    Note what did not happen

    It did not start building. propose hard-stops by design — even when your request said "build". Starting implementation takes a new message, and that boundary is the whole product.

    If it asks you something here, answer it properly

    The propose workflow is instructed to ask about anything that would materially change scope, observable behaviour or acceptance criteria, and to assume quietly on everything smaller. So a question at this stage is load-bearing by construction. "Whatever you think" converts a question the agent knew it couldn't answer into an assumption buried in a spec.

  4. Read the four documents — this is the step the method exists for

    docs/workflow.html §04 has the order to read them in and what each one is for. What it does not tell you is the trick that actually finds defects: read the specs against the four specs: rules in openspec/config.yaml literally, one rule at a time. Not "does this look right" — "does every collection requirement cover zero, one and many; is every date requirement split into server-neutral and client-derived".

    openspec/changes/timeline-baseline/proposal.md — excerpt

    ## Audience

Serves credibility only. Neither funnel runs through /timeline: sponsors reach
the sponsorship PDF from Galactic Summit, prospective members reach Join Us from
the navbar. Both are unchanged by this change.

## Content storage

Timeline Entry is git-resident — content/timeline/<id>/{index.json, en.mdx,
tr.mdx}, per design/content-model.md. No entity is split across git and Strapi.

## New runtime dependencies

None. This is the un-animated baseline. The scroll-linked L1 sequence is a
separate proposal against the same route and carries its own budget argument.

    Three sections, three of the proposal: rules, visibly answered. "Serves credibility only" is a valid and common answer here — it just has to be said out loud rather than left blank.

    openspec/changes/timeline-baseline/specs/timeline/spec.md — excerpt, as generated

    ## ADDED Requirements

### Requirement: Timeline route in both locales

The site SHALL serve the Timeline at `/en/timeline` and `/tr/zaman-cizelgesi`,
generated statically from `content/timeline/`.

#### Scenario: Entries render in date order

- **WHEN** the route is generated
- **THEN** entries SHALL be ordered by `date`, most recent first

#### Scenario: Past entries are de-emphasised

- **WHEN** an entry's date is earlier than the current date
- **THEN** the entry SHALL render with `--color-state-past`

#### Scenario: No entries

- **WHEN** `content/timeline/` is empty
- **THEN** the route SHALL NOT be generated
- **AND** the home page's Timeline link SHALL NOT render
    Two defects in that excerpt. Find them before reading on.

    Both are the kind that survive a quick read: the formatting is right, the vocabulary is right, and each one is individually plausible.

    Defect one — a date requirement that computes time on the server. "WHEN an entry's date is earlier than the current date" has to be evaluated somewhere, and on a statically generated page the only "somewhere" is build time. The build's idea of now freezes at deploy. This is the rule the constitution states twice and ADR 0001 devotes rule 3 to, and it slid past because the sentence reads like a styling detail rather than a temporal one.

    It is also vacuous, which is the tell. The Timeline is backward-looking by definition — design/content-model.md is explicit that it is distinct from Schedule, which is the forward-looking one. Every entry is in the past. The requirement describes a condition that is always true, using a mechanism that is forbidden.

    Defect two — the collection covers zero and many, and not one. There is a "No entries" scenario and an ordering scenario, and nothing for the single-entry case. design/content-model.md calls it out specifically: at one entry the axis label and the "now" marker must still make the direction legible. A single entry is where a scroll-snap container has nothing to scroll and every direction affordance quietly stops working.

    Do not type the spec headings from memory

    ADDED Requirements, Requirement:, Scenario: and the WHEN / THEN bullets come from the schema's template rather than from convention, and the template is what openspec instructions specs --change "<name>" --json prints. The agent reads it there every time. If you are hand-editing a delta and the validator complains about structure, read the template — do not infer the shape from an excerpt on this page.

  5. Fix the plan — /opsx:update

    Name the defects precisely. Do not describe the fix you want unless you actually want that fix — the agent has read the same documents you have.

    You

    /opsx:update timeline-baseline — two problems in the spec.

    The "Past entries are de-emphasised" scenario computes now at build time, which ADR 0001 rule 3 forbids. It's also vacuous: Timeline is backward-looking, so every entry is past. Replace it with the direction affordance requirement that design/motion.md actually asks for.

    And the collection covers zero and many but not one. Add the single-entry case — content-model.md says the axis and the "now" marker still have to make the direction legible there.

    Agent

    runs openspec status --change "timeline-baseline" --json

    reads specs/timeline/spec.md, design.md, tasks.md

    Agreed on both. Three revisions, one at a time — say yes or no to each.

    1 · specs/timeline/spec.md — replace the de-emphasis scenario:

    #### Scenario: Direction is legible without motion

- **WHEN** the route renders with no JavaScript
- **THEN** an axis label and a "now" anchor SHALL be present at the
  leading edge
- **AND** the reading direction SHALL be stated in the page's own
  locale, not implied by layout alone

    2 · specs/timeline/spec.md — add the single-entry scenario:

    #### Scenario: Exactly one entry

- **WHEN** `content/timeline/` holds one entry
- **THEN** the axis label and the "now" anchor SHALL still render
- **AND** the layout SHALL NOT depend on the container overflowing

    3 · tasks.md — task 2.4 lists fixtures for zero and fifty entries; add one.

    One thing I did not change and want to flag: design.md still describes the entry card as image-led. image is optional in the content model. That is a real gap, but it is a different defect from the two you named — want it in this pass?

    You

    Yes to 1, 2 and 3. Leave the card for now — I want to see it fail in apply before I decide whether it's a design.md problem or a content-model one.

    Why it works

    Three edits, three confirmations, and one deliberate refusal. The agent surfaced a fourth problem instead of quietly folding it in — and declining it is a legitimate answer, not a missed opportunity.

    Confirm each edit rather than approving in bulk

    update shows every revision and writes only after you say yes, which is only a safeguard if you read them. "All of them, go ahead" is the same move as not reading the plan, one step later and with less excuse.

Walkthrough — building it

/opsx:apply is the only workflow that writes code, and the only one whose transcript is mostly the agent stopping to ask you things.

You

/opsx:apply timeline-baseline

Agent

runs openspec instructions apply --change "timeline-baseline" --json

reads proposal, specs, design, tasks from contextFiles

Using change: timeline-baseline. Schema: spec-driven. Progress: 0/9 tasks.

Note the lookup

context7 fired before the first line of App Router code, not after the first bug. On this project that is a rule, not a preference — the failure it prevents is silent and surfaces in production.

The pause that matters most

Four tasks in, the agent hits something the plan did not cover. What it does next is the difference between a useful agent and an expensive one.

Agent

Paused at task 4/9. Progress: 3/9.

Task 4 says "both locales for the three seed entries". content/timeline/first-launch/ has en.mdx and no tr.mdx. Three ways forward and I do not want to pick:

  1. Translate the English body into Turkish myself.
  2. Create tr.mdx with a Turkish slug and status: incomplete, minimal body — which triggers the visible notice in design/i18n.md.
  3. Stop; the entry is not ready to ship.

I'll note that (1) is ruled out by the constitution — do not machine-translate and publish — but I'd rather say that than assume which of (2) or (3) you want.

You

(2). That's exactly what status: incomplete is for — CI needs both files and both slugs to exist, and the notice tells a Turkish visitor the truth. I'll get a real translation before we merge; if it doesn't arrive, the notice ships and that's fine.

Agent

writes content/timeline/first-launch/tr.mdx with slug: ilk-ucus, status: incomplete

Resuming task 4/9.

Why it works

The agent found a fork the plan did not anticipate, ruled out the forbidden branch itself, and refused to guess between the two legitimate ones. Answering "continue" here would have picked one at random and written it into the repository.

A pause is a question. Answer it with a decision.

"Continue", "you decide" and "whatever's simplest" are all the same instruction: pick one and don't tell me which. The apply workflow is specifically instructed to surface added scope rather than absorbing it — waving that through converts a visible decision into an invisible one, which is the exact trade the whole process exists to prevent.

The second pause — and why it goes back to the plan

Later, the card gap from §03 surfaces exactly where you left it.

Agent

Paused at task 6/9. design.md describes the entry card as image-led — image on top, caption beneath. image is optional in design/content-model.md, and two of the three seed entries have none. Rendering them in the described card leaves a hole.

I can build a no-image variant now, but that is a layout decision the design document does not make, and adding an image-less record would then require reading the component to know what happens. That looks like the design defect the apply guidance says to report rather than absorb.

You

Agreed, report it. Stop here — I'll run /opsx:update on design.md so the decision lands in the plan, then you resume from task 6.

Why it works

The fix is four sentences in design.md either way. Making it there means the reviewer sees a decision; making it in the component means they see a component and have to reverse-engineer the decision from it.

Validating what you built

Three layers, and they check genuinely different things. Only the third one is interesting.

LayerHowWhat it actually proves
The artifacts are well-formed npx openspec validate --all --strict Structure only. It does not read your requirements for sense, and a spec can be perfectly valid and describe the wrong system.
The code obeys the budgets Tier A on push; Tier B on the PR Typecheck, lint, the import-graph rule, first-load JS, the four static motion checks, locale parity. All mechanical, all worth having, none of them opinions.
The thing does what the spec said You, reading the delta beside the diff The only layer that can catch "built beautifully, specified wrongly". No gate on this project attempts it and none ever will.

For this change specifically, there is a fourth check that no tool performs and that takes about ninety seconds: show the page to somebody who has never seen it and time how long they take to say which end is older. design/motion.md sets the bar at one second. If they cannot, the baseline is wrong, and no amount of scroll-linked polish in the next change will fix it.

Asking the agent to check its own work

You

Before I open the PR: read openspec/changes/timeline-baseline/specs/timeline/spec.md and the diff on this branch, and tell me which scenarios are not demonstrably satisfied by the code. Don't fix anything — just list them and say what evidence is missing for each.

Agent

… reads both, walks the scenarios in order …

Seven of nine are satisfiable by reading the code. Two are not:

  • "Exactly one entry" — the fixture exists but nothing renders it. There is no test and no route that exercises the one-entry case, so the scenario is asserted, not demonstrated.
  • "Direction is legible without motion" — the axis label and anchor are present in both locales. Whether they make direction legible is not a property of the code.
Why it works

"List what is not demonstrated, fix nothing" is a much better question than "is this done". It asks for evidence rather than for a verdict, and an agent asked for a verdict will almost always supply one.

Then the pull request. .github/PULL_REQUEST_TEMPLATE.md asks for both locales, no new dependency, nothing computing now on the server, and — because a route changed — hreflang, the language switcher preserving the route, an /impeccable critique run, and the first-load number. Fill it in honestly; delete a section only when it genuinely does not apply.

After the merge, on main: /opsx:archive. Say yes to the spec sync. Skipping it leaves openspec/specs/ describing a site that no longer exists, which is worse than having no permanent specs at all — a stale spec is read as current by exactly the person this repository is written for.

05

Walkthrough — the L1 pass

Same route, second change, and almost none of the previous section applies. Motion work has its own failure modes, and the first one happens before you type anything.

The baseline shipped. Now the scroll-linked sequence — the reason this site is animation-forward at all. This is one of exactly two routes site-wide where an animation library is permitted, and that fact belongs in the first sentence of the prompt rather than being rediscovered by the agent halfway through a proposal.

The prompt that produces a good answer to the wrong question

You

make the timeline animate nicely on scroll

Agent

… no skill matched "nicely" …

Proposes a smooth-scroll wrapper, a spring on the card hover, and a parallax on the entry images.

Why it fails

Three separate policy violations, all plausible, none flagged: a second scroll system, a spring at L3 where CSS-only is absolute, and motion attached to an image the content model marks optional.

The prompt that spends its first sentence on the budget

You

/opsx:propose timeline-scroll-sequence — the L1 scroll-linked pass over /[locale]/timeline, which is one of the two permitted L1 routes.

Budgets are in design/motion.md; the library is dynamically imported and must stay out of first-load. The baseline from timeline-baseline keeps working with JavaScript off — it is the product, this is enhancement over it. Reduced motion and mobile are part of the proposal, not a follow-up; mobile always gets the native baseline.

Load gsap-core, gsap-scrolltrigger and gsap-react — not the rest of the suite — and check the current APIs with context7 before writing any of it into design.md.

Agent

runs npx ctx7@latest library "GSAP" "ScrollTrigger scrub and pin"

runs npx ctx7@latest docs <resolved id> "gsap.matchMedia with a reduced-motion branch"

runs openspec new change "timeline-scroll-sequence"

… four artifacts …

Why it works

Every constraint that could have been violated is named before the agent has a chance to violate it — and the three skills that apply are named, so the other five stay unloaded.

What design.md has to say, and what to check that it said

The design: rules in the constitution are injected automatically, so you do not have to remember them — but you do have to check they were honoured. For a motion change, four specific things:

openspec/changes/timeline-scroll-sequence/design.md — excerpt

## Motion tier

L1, on /[locale]/timeline only. This is the second of the two L1 routes
permitted by docs/adr/0003-motion-stack.md; no third is introduced.

## Weight

gsap core + ScrollTrigger + @gsap/react, dynamically imported from the route
segment, in the deferred chunk only. First-load JS for the route is unchanged
by this change — if it moves, something was imported statically and the
import-graph rule in Tier A will fail before the budget check does.

## Reduced motion and mobile

Both branches live in a single gsap.matchMedia() call built in the same pass as
the animation, never added afterwards. Under prefers-reduced-motion the result
is the baseline itself — not the sequence played faster. Below md (48rem) the
route serves the native scroll-snap baseline; scroll-linked pinning loses to
address-bar resize on mobile browsers.

The tell of a design document that has not thought about reduced motion is the phrase "a shortened version". At L1 the correct reduced-motion result is usually the static baseline you already shipped — which is one more reason the baseline ships first.

The suggestion to decline

Agent

One option worth raising: ScrollSmoother would make the scrubbing feel considerably better on desktop, and it is a GSAP plugin rather than a new vendor — about 8 KB gzipped, comfortably inside the deferred chunk.

You

No. It is a second scroll system, which is a new runtime dependency under the proposal rules regardless of who ships it, and design/motion.md requires smooth-scroll to be fully disabled under reduced motion — so it buys feel on one branch and complexity on both. Take it out of the proposal; if someone wants it later it needs its own ADR.

Agent

removes the ScrollSmoother option from design.md

Removed. Scrubbing stays on native scroll.

Why it works

Two sentences, one pointer, one instruction. No argument, no re-litigating, and nothing quoted at the agent that it could have read itself.

Before the pull request

  • /review-animations on the diff. It is manual-only — it will never fire on its own, by design, because it is a deliberately hostile reviewer and firing it uninvited turns every motion edit into a fight. Invite it anyway. It is cheaper than the reviewer doing it.
  • The three declarations — tier and route, what a reduced-motion visitor sees instead, what a phone gets. An animation that cannot answer all three is not finished, and the PR template asks for all three.
  • The screen recording. Required, and not a formality: visual regression was deliberately dropped from CI, so the recording is the compensating control. A motion PR without one is not reviewable, and the right reviewer response is to say so and stop.
Do not automate the part that cannot be automated

The temptation at this point is to have the agent screenshot the animation at intervals and tell you whether it feels right. Do not build that. docs/adr/0004-verification.md says it plainly: it produces confident output about a question it cannot answer, and the confidence is worse than the silence. Motion determinism in CI asserts computed values at fixed progress points, which is a different question and an answerable one.

06

When the plan is wrong

There are five places a correction can live, they cost wildly different amounts, and the common mistake is reaching for the cheapest one when it cannot hold what you are putting on it.

Rung three is not for a changed intent

update revises a plan that is still the plan. When the intent has moved, bending the old change into the new shape produces a folder whose proposal argues for one thing and whose specs describe another — and it archives in that state, forever.

You

/opsx:update timeline-baseline — actually, forget the route. Put the whole thing on the home page as a section and drop /timeline entirely.

Agent

That is not a revision of this change, it is a different change. The proposal's reason for existing is that the Timeline gets its own route — dropping the route invalidates the proposal, all four spec requirements, and six of the nine tasks. There would be nothing left of timeline-baseline except its name.

It also reverses an IA consequence recorded in docs/adr/0003-motion-stack.md: the route is why Timeline moved into the view-more list. Reversing it is an ADR-level move, not a planning one.

I'd start fresh — openspec new change "timeline-home-section" — and delete this folder if the route idea is genuinely dead. Do you want that, or do you want to talk through why the route stopped making sense first?

Why it works

It refused the tool and named the right one, twice: a new change for the plan, and an ADR for the decision underneath the plan. An agent that had obliged would have produced something that looked fine and was internally incoherent.

An abandoned change is not worth archiving — delete the folder and close the branch. The archive is for work that shipped.

07

When to push back

Every skill installed here is generic, competent and confident. Your project's decisions are specific and were made with information the skill does not have. When they collide, the recorded decision wins — and the way you say so matters more than you would expect.

The form of a good pushback

Name the document. Quote nothing. Say what you want instead. Three sentences is generous. Quoting the ADR at the agent puts a second copy of the rule in a transcript nobody will maintain, and the agent will read the file anyway — so the quotation adds drift and subtracts nothing.

Three collisions that will actually happen

"A scroll reveal on the missions archive would really lift it"

What it is: a third L1 route, proposed as a nice touch.

Say: "L1 is capped at two routes by docs/adr/0003-motion-stack.md and both are taken. If this is section-entry motion it is L2 and uses no library — propose that. If it genuinely needs to be L1, that is an ADR before it is a proposal."

The agent may draft the ADR. It may not accept one — an ADR is a team decision, and an agent writing and ratifying its own justification is the failure mode the whole authority chain exists to prevent.

"This drawer wants a spring — shall I add a motion library?"

What it is: the single most likely place for the policy to be argued with, and design/motion.md says so in those words.

Say: "Interface motion is CSS only here, no exceptions — design/motion.md. When the decision procedure arrives at 'reach for a spring', the answer on this project is a simpler interaction. Give me the CSS version."

A gesture that genuinely requires spring physics is a signal that the interaction is too ambitious for a promotional site, not a signal that the policy should bend. The skill is not wrong in general; it is overridden here, deliberately, in a document.

"The sequence comes to 52 KB — can we raise the cap to 60?"

What it is: a budget exception, requested as an implementation detail.

Say: "No. The cap is the constraint the technique has to fit, not a number we tune to the technique. Fit it, or propose a different technique. If you think the cap is genuinely wrong, that argument goes in a change proposal that raises its own route's cap explicitly and ships the static fallback first."

This is exactly the shape design/motion.md anticipates for a 3D hero: the budget does not quietly accommodate a technique, which is the entire reason the number was written down before the technique was chosen.

The one you will get every single session

If the impeccable hook is installed, its font guidance will flag Inter. That is a deliberate override — Orbitron lacks ğ Ğ ş Ş İ, so any heading containing them uses Inter — and it is recorded in design/brand.md. Dismiss it with a pointer to that file and move on. Do not re-litigate it, do not explain the reasoning again, and above all do not "fix" it by editing the skill: an edit under a skills/ directory diverges from the recorded hash and vanishes at the next sync, leaving you debugging behaviour that is no longer on disk.

What an agent may not decide alone
  • The stack. Settled in ADR 0001 and 0002; not open for renegotiation.
  • A third L1 motion route, or a second animation library. Both need their own ADR first.
  • Any budget exception. A cap is not raised because it would be convenient.
  • Anything an ADR decided. If an ADR is wrong, supersede it with a new one — never quietly diverge, and never edit an accepted one to match new reality.
08

Reviewing someone else's work

Agents are good at the half of review that is mechanical and bad at the half that matters. Use them for the first half so you have attention left for the second.

Read the spec delta before the diff

This is the whole reason the planning artifacts and the code travel in the same pull request. Reading the diff first anchors you to how it was built, and you will then evaluate the implementation against itself. Reading the delta first gives you the only question a reviewer can ask that a machine cannot: is this what we said we would build?

You

Read openspec/changes/timeline-baseline/specs/timeline/spec.md on this branch, then the diff. For each requirement, tell me whether the code satisfies it, contradicts it, or is silent on it. Do not fix anything and do not comment on style.

Agent

… reads the delta, then the diff …

Four requirements, eleven scenarios. Nine satisfied, one contradicted, one silent:

  • Contradicted — "no past/live/upcoming state in the generated HTML". The entry component adds a data-era attribute computed from date in a server component. It is invisible, and it freezes at build time exactly like a visible one would.
  • Silent — "exactly one entry". Fixture present, nothing renders it.
Why it works

Three verdicts, not two. "Silent" is the category that finds missing work — a binary pass/fail question would have marked the one-entry scenario as passing, because nothing about it fails.

The mechanical half

  • /impeccable audit, scoped to the changed files. Accessibility, performance, responsive, theming, scored P0–P3. Scoping is not a nicety: run across the whole repository it returns a wall of findings nobody reads; scoped to a diff it returns a review.
  • /review-animations if the diff contains motion. Manual-only — it will not fire on its own, so if you do not invoke it, nobody does.
  • Check the three motion declarations and the recording. If the recording is missing, stop reviewing and say so. That is not pedantry; it is the compensating control for a gate this project deliberately dropped.

The test no gate performs, and it takes two minutes

Adding a mission, talk, event, alumnus or sponsor must be a data operation. Nothing in CI checks this, and it is the rule most likely to be quietly broken by a component that looks fine with the three records it was built against.

You

On this branch, add a fourth timeline entry: no image, a one-line body, Turkish marked status: incomplete. Then tell me every file you had to touch other than the three content files — and if the answer is none, say so plainly.

Agent

creates content/timeline/static-fire-2/ with three files

None. The entry renders, the no-image variant applies, and the incomplete notice shows on the Turkish route.

One thing outside what you asked: at four entries the axis label overlaps the second card below sm. That is a layout bug, not a data one, and it is not covered by any scenario in the spec.

Why it works

Asking for the file list rather than for a verdict makes the answer checkable. And the request said "if the answer is none, say so plainly", which is how you get a clean negative instead of a paragraph that hedges toward finding something.

09

The change that should not be one

The process has a floor. Below it, the ceremony costs more than the work — and running it anyway teaches everyone that the ceremony is theatre.

The proposed threshold in docs/workflow.html §15 proposed is: if it changes observable behaviour or adds a dependency, it needs a change proposal. Typos, copy edits, a single content record, dependency bumps and broken links do not.

Adding a Stellar Talk is not a repository operation at all

You

Add a Stellar Talk for the propulsion lecture on the 12th — speaker, title, insight, and the YouTube link.

Agent

That one is not mine to do. Stellar Talk is Strapi-resident per design/content-model.md — it is a form in the admin panel, not a file in this repository. No branch, no proposal, and nothing for me to write.

If the form is missing a field you need, that is a change: a CMS schema addition, which needs a proposal because it alters what editors can publish.

Why it works

The correct agent response to a content request is to tell you where the form is. An agent that helpfully wrote a JSON file would have split an entity across git and Strapi — the one boundary this project draws at entity level and never at field level.

Two more that look bigger than they are

TaskRouteWhy
A typo in content/missions/apogee-1/tr.mdx Just fix it. fix/ branch, one commit. No observable behaviour changes. Locale parity still holds — both files still exist and still declare slugs — so a fix in one locale does not drag the other along.
Bumping a patch dependency Just do it. CI is the review. Not a new dependency. Tier A either passes or it does not, and that is a better answer than a proposal about it.

And one that looks like data and is not

"Add our first sponsor's logo" is a five-minute CMS task and it is blocked. design/content-model.md defers the sponsor showcase entirely: displaying a company's logo is using their trademark on a public website, and the sponsors have not been asked. The gate is permission collected and recorded somewhere durable — not components being ready.

The generalisation worth keeping

"Is this a change?" and "is this code?" are different questions. The things that most need a written decision on this project — sponsor permissions, alumni consent, sponsorship tiers — involve no code at all, and the things that involve the most code are often routine. Sort by consequence, never by diff size.

10

Patterns that work

Nine habits, each demonstrated somewhere above. None of them is about being polite to the agent and all of them are about making an answer checkable.

PatternWhat it buysSounds like
Name the artifact you want back The agent optimises for producing that thing rather than for sounding finished. "…and stop after the artifacts."
Point at documents, never paste them No second copy to drift, no context spent on something one tool call retrieves. "Budgets are in design/motion.md."
Say what you already know Saves the round trip, and makes your belief correctable if it is wrong. "I know /timeline is one of the two L1 routes."
Ask for the traps by name Zero, one, many; both locales; reduced motion; mobile. Cheaper to request than to catch. "It has to read correctly at zero and one entries."
One axis per iteration You can tell which of your instructions caused which part of the change. "Only the spec this round. Leave tasks alone."
Give it the output, not your description of the output Your paraphrase of an error is a lossy summary of the thing that already exists in your terminal. Paste the failing Tier A log.
Ask for evidence, not for a verdict An agent asked "is this done?" will supply an answer. Asked "what is not demonstrated?" it supplies a list. "List the scenarios the code is silent on."
Answer a pause with a decision Keeps the choice visible. "Continue" makes it invisible and permanent. "(2) — that's what status: incomplete is for."
Prefer "propose it" to "build it" For anything you would have to review anyway, four documents is a cheaper review than a diff. "Propose it; I'll read it before we build."
11

Patterns that don't

These are about collaboration, not economy. docs/agent-skills.html §12 covers the money — loading suites "to be safe", vague prompts that route nowhere, hand-editing vendored skills. This list is what goes wrong when the right skill loaded and the conversation still failed.

Anti-patternWhat it costsInstead
"Just build it" into /opsx:propose It hard-stops regardless, so you have spent a turn and received a plan you were not in the mood to read. You then read it badly. Decide which you want before typing. If you want code now, you want /opsx:apply against a change that already exists.
Arguing with the plan in chat You reach agreement, the artifact still says the old thing, and the reviewer reads the artifact. Take it up the ladder in §06. A correction that is not in a file did not happen.
Answering a pause with "continue" The agent picks one branch and writes it into the repository. The decision is now invisible and nobody knows it was made. Pick a branch and say why in half a sentence. The why is what makes it reviewable.
Approving artifacts without reading them You bought the ceremony and threw away what it bought. You now review a thousand lines instead of four documents, later, with more sunk cost. Read them in order and stop at the first thing that is wrong — everything downstream was built on it.
Pasting an ADR into the prompt A second copy of a rule inside a transcript nobody maintains, plus the agent treating your paste as authority when the file has moved on. The path is the citation. It will read the file.
"Mark the rest of the tasks done" tasks.md now lies. archive folds a lie into the permanent specs, where it is read as current by someone in 2029. Leave them unticked. An interrupted change resumes exactly where it stopped — that is what the checkboxes are for.
Accepting a machine translation Forbidden outright: both locales are first-class, and a visibly machine-translated Turkish page is worse than an honest notice. status: incomplete with a placeholder body. The visible notice is the supported way to ship a translation backlog.
Asking for a screenshot loop to judge motion Confident output about a question it cannot answer — and the confidence is worse than silence, because it displaces the human who could have answered. Record the screen. Watch it. Watch it again the next day.
Letting the agent write and accept an ADR The authority chain collapses: the thing that was supposed to constrain the agent is now written by it. An agent may draft one. A person accepts it, and the acceptance is the part that matters.
The one-sentence version

Every anti-pattern above is the same mistake in a different costume: a decision made somewhere it will not survive.

12

Iterating without drifting

Long sessions decay. Not because the agent gets worse, but because the wrong turns stay in the context and start outweighing the right ones.

The loop that keeps its footing

  1. Read the artifact on disk — not the summary in the chat. They diverge, and the file is the one that ships.
  2. Name one thing that is wrong with it, as specifically as you can.
  3. Confirm the edit the agent proposes, or reject it. One at a time.
  4. Re-read. Then decide whether to go round again.

The temptation is to batch: five corrections in one message, because typing them individually feels slow. Batching costs you the ability to tell which instruction produced which result, and when one of the five was misunderstood you cannot tell which one from the output. Two rounds of three is not slower than one round of five once you count the round that untangles it.

When to abandon the session entirely

After a long wrong turn — an approach explored for twenty minutes and discarded, a misunderstanding corrected three times — the context is now mostly a record of things that are not true. Start a fresh session.

This costs almost nothing here, and that is not an accident. The change folder is the save file. A new session reads openspec/changes/<name>/ and tasks.md tells it exactly which task was in progress. That property is most of the argument for spec-driven development on a team with annual turnover — the same mechanism that survives a graduating contributor survives a poisoned context window.

You

/opsx:apply timeline-baseline — fresh session. Read the artifacts and the branch before you do anything, and tell me where you think we are before you resume.

Agent

runs openspec instructions apply --change "timeline-baseline" --json

5/9 complete. Task 6 — the entry card — is unticked, and design.md was revised at 14:20 to add the no-image variant, after the last tick. So the plan moved and the code has not caught up yet. Resuming at 6.

Why it works

"Tell me where you think we are before you resume" costs one sentence and catches the case where the fresh session has misread the state — before it writes anything.

Handing off to a person

The handoff is the branch and the change folder. It is not the conversation, and it is not a summary you write into a chat message. If something matters and lives only in a transcript, move it up the ladder in §06 before you hand over — because you are the last person who will ever be able to.

Motion is the exception to iterating fast

Everything above assumes you can evaluate the result immediately. For motion you cannot: the fifth viewing of an animation tells you nothing the first four did not, and your judgement of timing degrades as you get used to it. Play it at 2–5× duration, step it in the animation inspector, test it on a real device, and look again tomorrow. That is slower than a loop and it is the only method that works.

Phrasebook

Openers to fill in and send. They are shaped, not scripted — the point is that each one carries all four parts from §02.

Thinking, before you know what you want

/opsx:explore — I want to build <thing>. Before we propose anything:
<the specific thing you can't resolve>. What are the options, and what
do the design documents already decide for me?

The second sentence is what separates explore from chat. Without it you get a survey; with it you get the consequence you had not spotted.

Proposing

/opsx:propose <kebab-case-name> — <what it is, in one line>.
<Scope boundary: what this change is deliberately NOT.>
<Storage: git or Strapi. Locales. Zero/one/many. Motion tier if any.>
Constraints are in <path> — point at it, don't restate it.
Stop after the artifacts; I'll read them before we build.

Line two is the one people skip and the one that prevents the most rework. Saying what a change is not is how the scope survives contact with a helpful agent.

Reading the plan back

Before I read this properly — walk the specs against the four `specs:`
rules in openspec/config.yaml, one rule at a time, and tell me where
they don't hold. Don't fix anything.

Makes the agent do the mechanical pass so your attention goes to intent. It is also a fair test of the artifacts it just wrote, and it does sometimes find its own omissions.

Correcting the plan

/opsx:update <name> — <defect one, named precisely, with the document
that makes it a defect>. <defect two>. Show me each edit before you
write it.

"With the document that makes it a defect" is doing real work: it turns your objection from a preference into something the agent can verify and, occasionally, correct you on.

Building

/opsx:apply <name>

# and when it pauses — a decision, plus half a sentence of why
(2) — that's what <mechanism> is for, and <the reason>.

Nothing more is needed at the start. The plan is the prompt; adding instructions here means they exist outside tasks.md, which is where they will be lost.

Checking before the pull request

Read the spec delta on this branch, then the diff. For each requirement,
say whether the code satisfies it, contradicts it, or is silent on it.
Don't fix anything and don't comment on style.

Three verdicts rather than two. "Silent" is the category that finds missing work, and a pass/fail question cannot express it.

Declining something

No — <document> decides that. If you think it's wrong, that's an ADR,
not a proposal. Give me <the version that fits> instead.

Name, route, redirect. Every additional sentence is you re-litigating a decision that is already written down.

14

What this page cannot teach you

Stated plainly, so nobody mistakes a fluent transcript for a solved problem.

  • Whether the result is any good. Every transcript here ends with an artifact or a diff. None of them ends with taste. Whether the Timeline reads as intentional, whether the hero earns its weight, whether a sponsor is impressed — no prompt produces those and no gate measures them.
  • Whether the content is true. No CI gate checks that a stated apogee is correct, and an agent will format a wrong number beautifully. Missions are in git under review for exactly this reason.
  • What the agent will actually say. These are composites, written against the skills installed on 2026-08-17. Wording changes with every model and every skill sync. The shape survives longer than the words — if a transcript here stops matching reality, the lesson underneath it probably still holds, and it is the lesson that was worth writing down.
  • How to work without the tooling. A fresh clone has none of it, deliberately. Someone with no skills installed can still read every document, make every change and open every pull request. The agents make the work faster; they are not a dependency of it, and if they ever become one, something has gone wrong that no skill will fix.

If something here is wrong

Fix it. It is a tracked file — docs/openspec-practical-examples.html — and it goes through the same review as anything else. If it disagrees with docs/workflow.html or docs/agent-skills.html, all three are worth checking and one of them has a bug; say which when you report it. If it disagrees with an ADR, this page is the one that is wrong.

KUASAR Air to Ground — worked examples only. It decides nothing and deliberately restates nothing: docs/workflow.html owns the process, docs/agent-skills.html owns skill routing, and every decision either of them refers to lives in docs/adr/ and design/.

Every transcript is set after the scaffold exists and none of these commands runs against the repository as it stands today — see §01. Palette and type derive from design/tokens.md, and there is no orange anywhere on this page: it is reserved for launch, live, upcoming and the primary call to action, and a page of worked examples is none of those.
