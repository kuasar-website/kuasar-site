01

Read this first

This document describes how we work. It decides nothing on its own.

Everything about what was decided and why lives in the architecture decision records and the design system. This page points at them and never restates them, because two copies of a rule drift apart and then nobody can tell which one is current. If something here appears to contradict an ADR, the ADR wins and this page has a bug — fix it.

Where authority actually sits

RankSourceWhat it governs
1 openspec/config.yaml The project constitution. Injected into every generated planning artifact, so it is deliberately short — rules and pointers only.
2 docs/adr/ The decisions, and more importantly the reasoning. Read one before undoing what it decided.
3 design/ The design system those decisions produce: tokens, motion, content model, i18n, brand.
4 docs/workflow.html This page. Process only.
The constraint behind everything

Five contributors, annual turnover. Everyone who builds this graduates. Every artifact — code, spec, commit message — is written for someone who joins in three years and finds nobody left who built it. That single constraint explains most of what looks over-engineered here.

If you have just inherited this project and nothing else, read docs/HANDOVER.md first. It covers accounts, the domain, backups and deploys — the things that break irrecoverably. This page covers the daily work.

02

Set up your machine

Four steps, then a warning about what your clone will look like.

1 · Runtime

Node 22 LTS and pnpm. corepack enable is the least painful way to get a pnpm that matches the one the deploy platforms use.

2 · Clone

git clone https://github.com/kuasar-website/kuasar-site.git
cd kuasar-site

3 · Install the OpenSpec commands

The /opsx:* commands are not in the repository — each person installs them into their own agent. This writes the command and instruction files for the tools you name: 

npx openspec init --tools claude,codex,agents

Already installed and out of date? npx openspec update. The CLI is pinned at v1.9.0; npx openspec --version tells you what you actually have, and it is worth checking, because published OpenSpec documentation is currently a few versions behind the CLI and describes commands that may not exist in your install.

4 · Install the agent skills

Design, motion and GSAP skills come from the organisation's own tooling rather than from this repository. See Open items — the exact install command needs to be written down by whoever set it up.

Your clone will look half-empty. That is correct.

.claude/, .agents/, .impeccable/ and skills-lock.json are gitignored on purpose: anyone in the organisation can install them, so they are not the repository's business. A fresh clone having none of them is not a broken checkout, and they must never be committed.

There is also no application to run yet

No package.json, no apps/, no build, lint or test commands. Everything in README.md under Running it locally is marked aspirational for exactly this reason. Do not invent commands — nothing runs yet. Section 08 is how that changes.

The map

The one rule to memorise

Missions and the timeline live in the repository. Everything else lives in Strapi.

That boundary is drawn at the entity level and never at the field level. Half an entity in git and half in the CMS spares perhaps one pull request a year and costs every future editor an inexplicable half-empty record. 04

The loop

This is the spine of the whole document. Work moves through it in one direction.

  1. Ask whether this is a change at all

    A typo, a copy edit, a dependency bump or adding one content record does not need a proposal — the ceremony would cost more than the work. Everything else does. The threshold: if it changes observable behaviour or adds a dependency, it needs a change. See the proposed threshold below.

  2. Think first, if you need to — /opsx:explore

    Optional. Explore mode is a thinking partner: it reads code, maps what exists, compares approaches and draws diagrams, and it will not write code. Use it when you do not yet know what you are building. Skip it when you do.

  3. Branch

    git switch -c change/<change-name>

    Branch before you propose, so the planning artifacts are versioned with the work from the first commit.

  4. Draft the plan — /opsx:propose <name-or-description>

    Creates openspec/changes/<name>/ and fills it: proposal.md (what and why), specs/<capability>/spec.md (the requirements, as a delta — only what changes), design.md (how) and tasks.md (the plan of work). It will ask you questions where the scope is genuinely ambiguous.

    It will stop, and that is not a malfunction

    /opsx:propose is planning-only and hard-stops. It refuses to write implementation code in the same response — even if your request said "build the timeline". Starting implementation takes a new request. This surprises everyone once.

  5. Read the plan yourself

    This is the step people skip, and it is the step the whole method exists for. Reviewing four short documents is cheaper than reviewing a thousand lines of code. Read them in this order and stop as soon as something is wrong:

    OrderFileWhat you are checking
    1proposal.mdThe intent and scope. If this is wrong, stop here — everything downstream is built on it.
    2specs/…/spec.mdThe requirements. The heart of the review: are they observable, bilingual, and do they cover zero, one and many?
    3design.mdThe technical approach. Larger changes only.
    4tasks.mdThe plan of work. Does the un-animated baseline come first?

  6. Fix the plan if it is wrong — /opsx:update

    Revises the artifacts that already exist and reconciles them against each other, confirming every edit with you before writing. It never touches code. If the change's intent has shifted rather than its details, do not bend the old change into the new shape — start a fresh one.

  7. Build it — /opsx:apply

    Works through tasks.md one task at a time, ticking - [ ] to - [x] as it goes, so an interrupted session resumes exactly where it stopped. It pauses rather than guessing when a task is ambiguous, and it surfaces added scope instead of quietly absorbing it — if it stops to ask, answer it rather than telling it to continue.

  8. Commit, push, open the pull request

    The planning artifacts and the code go in the same pull request. A reviewer reads the spec delta beside the diff that implements it — that pairing is most of the review's value. Fill in .github/PULL_REQUEST_TEMPLATE.md honestly; see section 10.

  9. Review and merge

    A peer reviews; the merge checker merges. A pull request touching motion is not reviewable until the screen recording is attached — feel is not automatable and no CI gate substitutes for a human watching it.

  10. Close the loop — /opsx:archive

    Run it after the merge, on main. It checks the artifacts and tasks are complete, offers to fold the delta specs into openspec/specs/, then moves the change folder to openspec/changes/archive/YYYY-MM-DD-<name>/. Say yes to the sync — that is how the permanent specs learn what your change did. Skipping it leaves the specs describing a system that no longer exists.

05

Command reference

Six workflows, reachable two ways: type the slash command (/opsx:propose), or invoke the skill by name (openspec-propose). Same workflow either way — the slash commands are just the shorter door.

CommandWritesNever doesLeaves you
/opsx:explore Nothing, unless you ask it to capture the thinking as artifacts Write or change code With a clearer problem
/opsx:propose The whole change folder: proposal, delta specs, design, tasks Implement — it hard-stops, deliberately With a plan to read
/opsx:update Revisions to artifacts that already exist Touch code, or create artifacts that do not exist yet With a coherent plan
/opsx:apply Code, plus tick marks in tasks.md Silently narrow or defer specified behaviour Ready to open a PR
/opsx:sync Folds delta specs into openspec/specs/ Archive anything With current main specs
/opsx:archive Offers the sync, then moves the change into changes/archive/ Archive while a sync is still running At a clean slate
Two commands you will see referenced but do not have

The installed workflows sometimes suggest /opsx:continue or /opsx:new. Neither is installed here. When one is suggested, use the CLI instead: openspec status --change "<name>" --json shows the next artifact, and openspec instructions <artifact-id> --change "<name>" --json explains how to create it. Published OpenSpec documentation describes a few other commands for the same reason — it is written against a different version.

When to reach for /opsx:sync on its own

Rarely. /opsx:archive runs the sync for you as part of archiving, which is the normal path. Standalone sync is for when you want the permanent specs updated before the change is finished — a long-running change whose first half has shipped, for instance.

06

Reading the state

These are read-only and safe to run at any time. Use them instead of guessing what state a change is in. 

npx openspec list                      # active changes, most recent first
npx openspec list --specs              # the permanent specs instead
npx openspec status --change "<name>"  # which artifacts exist, what is blocked
npx openspec show "<name>"             # read a change or a spec
npx openspec view                      # interactive dashboard of both
npx openspec validate --all --strict   # the check CI would run
npx openspec doctor                    # relationship health of the openspec root

status is the one to learn. It reports file existence, not correctness — so an artifact reading done means the file is there, not that it is any good. That is what step 5 of the loop is for.

07

What a good proposal does here

openspec/config.yaml carries a rules: block for each artifact type, and those rules are injected automatically when the artifact is generated. You do not have to remember them. But knowing what they ask for tells you what to check when you read the plan back — and a generated artifact that ignores one is a defect worth catching.

proposal.md must

  • State which audience the change serves — sponsors, prospective members, or neither. "Serves credibility only" is a valid and common answer, but it has to be said out loud.
  • Name each entity's storage location if content is added, and confirm nothing is split across git and Strapi.
  • Declare any new runtime dependency. A second animation library, a second scroll system, or a third L1 route needs its own ADR before the proposal is viable.

specs must

  • Describe observable behaviour in both locales. A requirement that only holds in English is incomplete, not merely untranslated.
  • Separate the neutral server-rendered form of any date from the client-derived past/live/upcoming state.
  • Express reduced-motion and mobile fallbacks as scenarios, not as prose asides.
  • Cover zero, one and many entries for every collection.

design.md must

  • Name the motion tier (L1/L2/L3) of every animation, and the route it lives on.
  • State the per-route first-load JS impact, and whether any import reaches an animation library from a non-L1 route.
  • Say whether a new Strapi field is needed, and whether it is locale-specific.
  • Point at the ADRs and design documents rather than restating them.

tasks.md must

  • Order the work so the un-animated, reduced-motion baseline ships before anything built on top of it.
  • Include both locales wherever user-facing copy is added.
  • Name which CI gate covers the change — and if none does, say so rather than implying coverage.
While implementing

Keep the un-animated baseline working at every commit; never leave the site in a state where the enhancement is required for the page to function. And add content as data — if adding a record seems to require editing a layout, stop and report it. That is a design defect, not a task detail.

First changes, in order

Nothing is built yet, so the loop above has nothing to run against. This is a starting sequence, not a schedule — each of these should become a real change proposal that can argue with the ordering.

#ChangeWhy here

2 CI Tier A and apps/web/budgets.json The import-graph rule and the weight budget are worth far more before the code exists than after. Retrofitting a budget onto a built site means deleting work.

7 The L1 signature sequence Last. ADR 0003 deliberately does not decide the technique; that proposal must argue its own budget and ship the static fallback first. The site is launchable without it.

Whether sponsors are ranked into tiers — decide it before the first sponsor is added, because changing it later means renegotiating with people who were promised a tier. And Vercel's commercial-use question in ADR 0001, which has a deadline attached: the Galactic Summit.

09

Six rules that will bite you

Each of these is enforced somewhere — in CI, in review, or by the shape of the system. One sentence each; the reasoning is in the linked document.

1 · Motion is tiered, and most of the site may not use the library

L3 micro-interactions are CSS only, no exceptions; L2 section motion uses no library; L1 signature motion may use GSAP, dynamically imported, and is capped at two routes site-wide — the home hero and /[locale]/timeline. A third L1 requires its own ADR.

The tie-break when a tier is not obvious: if it responds to a pointer it is L3; if it responds to a section entering the viewport it is L2; if someone would call it "the animation", it is L1 and needs a route budget. docs/adr/0003-motion-stack.md

2 · Nothing computes "now" on the server

Pages are static and are not rebuilt when a date passes. The server ships raw ISO dates and renders the neutral form; a client component derives past/live/upcoming after mount. A calendar that computed "this month" at build time is wrong within weeks. Never add a cron or time-based revalidation to work around this. docs/adr/0001-stack.md, rule 3

3 · Adding content is a data operation

Adding a mission, talk, event, alumnus or sponsor must require adding data only — never editing a component or a layout. Every collection renders sensibly at zero, one and fifty entries. If a record needs a layout edit, that is a defect to report, not a task to complete. design/content-model.md

4 · Both locales, always, in the same pull request

Turkish and English are both first-class; neither is a translation of the other. Git content needs both locale files and a slug in each — a missing Turkish slug is a broken route, not a missing translation, and CI blocks it. A locale file may declare status: incomplete to show a visible notice; that is the supported way to ship a translation backlog. Do not machine-translate and publish. design/i18n.md

5 · No third-party analytics, embeds, pixels or tag managers

The KVKK position is unresolved, so the surface stays as small as it can be. Vercel Web Analytics and Speed Insights are in; everything else is out. Google Forms may be linked, never embedded. docs/adr/0002-cms.md

6 · Orange means one thing

Launch, ignition, live, upcoming, primary CTA. Nothing else — there is deliberately no general-purpose orange token. The reviewer's test: if a proposed use of orange is not one of those, it is wrong regardless of how good it looks. Related: no global neon, no glow, no gradient washes. The site must not read as gaming. design/tokens.md

10

Before you open a PR

Fill in .github/PULL_REQUEST_TEMPLATE.md properly. Delete a section only when it genuinely does not apply — never because it is inconvenient.

What CI runs

Gates are tiered by cost, because this is a private repository with 2,000 Actions minutes a month and the failure mode of running out is CI stopping for everyone, mid-month.

TierWhenTargetWhat it asserts
A Every push, every branch < 2 min Typecheck · lint · the import-graph rule · first-load JS budget · four static motion checks · locale parity
B PRs to main, path-filtered < 10 min Lighthouse · axe-core across generated routes · motion determinism where an L1 exists

The import-graph rule is the load-bearing one. Because the animation library is dynamically imported it never shows up in first-load JS, so a weight budget alone would happily pass a route that pulled GSAP into the shared chunk. The import rule catches that at zero bytes and zero CI seconds. docs/adr/0004-verification.md

Removing a path filter to "just be safe" is a budget decision, not a convenience decision. Path filtering is what keeps the minute budget viable.

What CI cannot see

  • Whether an animation feels right. Timing, easing and whether a sequence reads as intentional are human judgements. A motion PR attaches a short screen recording and the reviewer watches it. Do not build an agent screenshot loop to substitute — it produces confident output about a question it cannot answer.
  • Layout drift. Visual regression was deliberately dropped: screenshot baselines are binaries that churn on every intentional design change, which is the same failure mode that keeps media out of git. The screen recording and human review are the compensating control, not a nice-to-have.
  • Real-device performance. Lighthouse runs on a CI runner, not on a phone on a Turkish mobile network. Vercel Speed Insights is the only thing reporting back from reality — which is why the whole motion policy is falsifiable only through it.
  • Whether the content is true. No gate checks that a stated apogee is correct.

Every animation declares three things

Tier:            L1 / L2 / L3, and the route
Reduced motion:  what a reduced-motion user sees instead
Mobile:          what a phone gets

An animation that cannot answer all three is not finished. A reduced-motion path means a genuine non-animated path — the same sequence played faster is not an implementation.

11

Working with agents

Agent-assisted development is assumed here — it is one of the reasons the stack was chosen. That makes a few habits load-bearing.

Check the docs before writing against an API

Next.js App Router, Strapi 5 and GSAP all move faster than model training data, and the failure is quiet. Next 16's revalidateTag takes a second cache-profile argument that Next 15's did not: copy a pre-16 example and it typechecks, passes review, and silently under-revalidates. Fetch current documentation rather than trusting recall.

Which skill owns which question

QuestionAuthority
Anything GSAPgsap-* skills — core, timeline, ScrollTrigger, react, plugins, performance
Interface motion: hover, focus, press, toastsemil-design-eng, animate, apple-design
Interface critique, layout, hierarchyimpeccable
The spec workflowThe openspec-* skills and this page

The two motion budgets stay separate. The interface-motion skills govern L3 and L2 only; they have no authority over narrative motion, and narrative motion guidance has no authority over a button hover. design/motion.md

What an agent may not decide alone

  • The stack. It is settled in ADR 0001 and 0002 and is not open for renegotiation.
  • A third L1 route, or a second animation library — both require their own ADR first.
  • Any budget exception. A route's first-load cap is not raised by an agent noticing it would be convenient.
  • Anything an ADR decided. If the ADR is wrong, write a new ADR that supersedes it — do not quietly diverge.

Two local details

  • If the impeccable hook is installed, UI edits get critiqued automatically and the feedback arrives as hook output. It needs node on PATH; without it, it silently does nothing. Not having it is not an error.
  • Its font guidance flags Inter. That is deliberately overridden here for Turkish glyph coverage, and recorded in design/brand.md. Dismiss it with a pointer rather than re-litigating it every run.
  • Never hand-edit anything under a skills/ directory — edits diverge from the recorded hash and vanish at the next sync.
12

Unusual situations

You got pulled onto something else mid-change

Nothing breaks. Changes are folders, not sessions. Propose the second change, work it, archive it, then /opsx:apply <first-change> — it resumes at the first unticked task. Keep them on separate branches.

The change turned out to be a bad idea

Delete the folder under openspec/changes/ and close the branch. An abandoned change is not worth archiving; the archive is for work that shipped.

The change has no specs — docs, CI, tooling

Archive with npx openspec archive "<name>" --skip-specs. Nothing about observable behaviour changed, so there is no delta to fold into the permanent specs.

You need to change something an ADR decided

Write a new ADR that supersedes it. Number it in sequence, mark the old one superseded, and record why the original reasoning no longer holds. The ADRs are a record of thinking over time — editing an accepted one to match new reality destroys exactly the thing that makes it useful in 2029.

You resolved or invalidated an ASSUMPTION:

There are 20 ASSUMPTION: lines across 10 files. They are deliberate, marking things that were assumed rather than verified. Find them with: 

grep -rn "ASSUMPTION:" docs design openspec

If your work settles one, correct the document in the same pull request rather than leaving it to drift. Archiving prompts you to do this; take the prompt seriously.

Something in this document is wrong

Fix it. It is a tracked file — docs/workflow.html — and it goes through the same review as anything else.

Glossary

TermMeans
ADRArchitecture Decision Record. One document per significant decision, recording the context, the decision, its consequences and the alternatives rejected. Never edited once accepted — superseded by a new one instead.
ArtifactOne of the planning documents in a change folder: proposal, specs, design, tasks.
CapabilityA named area of behaviour that specs are organised under — the directory under specs/.
Delta specThe requirements a change adds, modifies, removes or renames — not a full copy of the spec. Archiving folds the delta into the permanent spec.
First-load JSThe JavaScript a visitor downloads before the page is interactive, gzipped, per route. Capped on every route including L1 ones; the numbers live in design/motion.md and apps/web/budgets.json.
L1 / L2 / L3Motion tiers. L1 signature (library allowed, two routes only), L2 section (no library), L3 micro (CSS only).
KVKKTurkey's personal data protection law. Unresolved for this project, which is why third-party analytics and embeds are banned and why alumni consent fields are required.
On-demand revalidationStatic pages are rebuilt when the CMS publishes and pings the site — not on a timer. A timer is explicitly forbidden.
Reduced motionprefers-reduced-motion. Requires a genuine non-animated path, not a shortened animation.
Tier A / Tier BThe two CI gate levels — fast checks on every push, browser-based checks on PRs to main.

15

Proposed conventions

None of the following is settled anywhere in the repository. They are proposals, marked the way the ADRs mark their own assumptions, so that the team has something concrete to argue with rather than a blank. Ratify, amend or replace them — but decide, because five contributors improvising five conventions is the outcome nobody wants.

Branch names proposed

change/<openspec-change-name> for anything with a change proposal, so git branch and openspec list read the same. fix/<short-description> and content/<entity>-<slug> for work without one.

One change per branch, per pull request proposed

The pull request carries the spec delta and the code that implements it. Two changes in one branch means a reviewer cannot approve half of it.

Commit messages proposed

feat: fix: docs: content: chore:, with the change name in the body. Not enforced by CI — this is a readability convention, not a gate.

When to skip OpenSpec entirely proposed

Typos, copy edits, adding a single content record, dependency bumps, and fixing a broken link. The threshold: if it changes observable behaviour or adds a dependency, it needs a change proposal. When genuinely unsure, propose — the proposal is four short documents, and being wrong the other way means an undocumented behaviour change.

Review proposed

One peer review plus the merge checker, per the team shape recorded in ADR 0001. A pull request touching motion is not reviewable until the screen recording is attached — the reviewer should say so and stop rather than approving on the code alone.

Archive after merge proposed

Run /opsx:archive on main, after the merge, by whoever authored the change. Archiving moves directories; doing it before the merge puts that move inside the pull request and makes the diff harder to read.
