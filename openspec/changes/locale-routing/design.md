## Context

See `proposal.md` — Why. Constraints that shape this design:

- `redirects()` in `next.config.ts` is evaluated by Next's routing layer from a
  static, build-time table — not a per-request function inspecting headers.
  `permanent: false` yields a `307`; `permanent: true` yields a `308`. This is
  the mechanism for the `/` → `/en/` redirect, and it satisfies
  `design/i18n.md`'s "no middleware" rule, which specifically objects to
  `Accept-Language` sniffing, not to a static redirect table. This is the
  **only** interaction this capability has with `next.config.ts`.
- Nested dynamic route segments support per-parent `generateStaticParams`: a
  child segment's `generateStaticParams` can receive the parent's already-
  resolved params (e.g. `locale`) and return only the params valid for that
  parent, rather than a full cross-product. This has been part of the App
  Router's static-generation model since early versions and is the mechanism
  behind this design's locale-specific segment resolution (see Decisions).
- Route params under `app/[locale]/` are consumed as a `Promise` in current
  Next.js major versions (`const { locale } = await params`).
- **Version caveat:** the API behavior above was checked against the publicly
  published Next.js docs (v16.3.4) via WebFetch, because no `context7` tool was
  available and `apps/web/node_modules` does not exist yet in this clone.
  `apps/web/package.json` pins `next@16.3.1` — a different patch version.
  `apps/web/AGENTS.md` (present in this repo, regenerated by `next dev`)
  explicitly warns that this Next.js version may diverge from training data
  and directs implementers to the *installed* version's own bundled docs
  (`node_modules/next/dist/docs/`) before writing code. Nested
  `generateStaticParams` is a long-stable feature and lower-risk; the
  `redirects()` status-code semantics and the `params`-as-`Promise` change are
  more recent and should be explicitly reconfirmed against the installed
  16.3.1 docs during `/opsx:apply`, before any code is written against them.
  Nothing in this design should be read as certain until that reconfirmation
  happens.

## Goals / Non-Goals

**Goals:**
- The exported `LOCALES` list and segment map give Dev 2's `site-shell`
  capability everything it needs to statically generate `app/[locale]/layout.tsx`
  for both `en` and `tr`, with `[locale]` established as a true root-level
  route parameter — locale-routing supplies the data; `site-shell` builds
  that file (`docs/task-assignments.html`).
- The Turkish/English segment map is expressed exactly once as data, and both
  routing and the language switcher/sitemap consume that one definition,
  skipping any entry marked unresolved.
- The requirement that lets a locale-prefixed but otherwise-unmatched request
  reach the locale-less 404 (owned by `i18n-hardening`) is specified here, as
  an obligation on `site-shell`'s `app/[locale]/layout.tsx` — this capability
  supplies the data (`LOCALES`) and the requirement, not the file that
  satisfies it.
- The implementation stays entirely within files Dev 3 already owns per
  `docs/task-assignments.html`. `next.config.ts` gains only the single fixed
  redirect, pending Dev 1 coordination — not performed by this change.
  `app/[locale]/layout.tsx` is Dev 2's file and is not created or edited here.

**Non-Goals:**
- Deciding how any individual section's content is fetched or rendered — that
  is each capability's own concern (`git-content-pipeline`, `announcements`,
  `alumni-directory`, and the not-yet-proposed section changes).
- Building the three error pages — `i18n-hardening` builds them; this design
  only guarantees the routing mechanism reaches the right one.
- Resolving what `projects`/`projeler` maps to. The segment map carries it
  forward marked unresolved, per `proposal.md` — Impact.
- Building route implementations for `(news)/`, `(alumni)/`, or any other
  section. `announcements`, `alumni-directory`, and every other section are
  separate, later capabilities — this change defines a reusable resolution
  pattern (Decision 1) that they, or any other capability, may adopt in their
  own proposals; it does not pull their route work forward.
- Mandating that any capability adopt this pattern. Whether `announcements`,
  `alumni-directory`, `missions`, `about`, `schedule`, `timeline`, `events`, or
  `summit` use it is each owning developer's own call, in their own proposal.
- Implementing or editing the switcher's visible markup, `components/shell/`,
  `app/[locale]/layout.tsx`, or `app/[locale]/page.tsx` — those belong to
  Dev 2 (INCO)'s `site-shell` capability (`docs/task-assignments.html`) /
  whoever composes the home page. This capability exports the data/behavior
  those files consume.

## Decisions

### A reusable locale-segment resolution pattern — no `next.config.ts` involvement, and no route implementations built by this change

`next.config.ts` is Dev 1 (BOOSTER)'s file, and this capability's only
justified interaction with it is the single, fixed `/` → `/en/` redirect.
Nothing about fully localized segments requires touching it further.

Locale-routing defines the reusable primitive that lets any future capability
serve a fully localized segment without a rewrite table: a
`resolveSegment(sectionKey, locale)` helper reading
`apps/web/lib/i18n/segments.ts`, paired with a documented route convention — a
dynamic `[segment]` folder whose `generateStaticParams` receives the parent's
already-resolved `locale` and returns only the one segment string valid for
that locale:

```ts
// Illustrative pattern — not a route this change builds
export async function generateStaticParams({ params }: { params: { locale: Locale } }) {
  const { locale } = params
  return [{ segment: resolveSegment(sectionKey, locale) }]
}
export const dynamicParams = false
```

Any locale/segment combination outside the generated set 404s (falling
through to `i18n-hardening`'s not-found page), with no rewrite table anywhere.

This change defines and documents the pattern and the `resolveSegment` helper.
It does **not** create `(news)/`, `(alumni)/`, or any other section's route
folder — `announcements`, `alumni-directory`, and every other section are
separate capabilities, proposed and built on their own schedule. Adopting this
pattern is each of those capabilities' own decision when their proposal is
written.

**Alternatives considered:**
1. *Generated `next.config.ts` rewrites* (an earlier draft of this design).
   Rejected: it required Dev 1 to carry Dev 3's routing logic in their own
   file, in tension with `docs/task-assignments.html`'s "one owner per path"
   principle and with `design/i18n.md`'s own preference for minimal moving
   parts around the redirect specifically.
2. *A catch-all resolver* (`app/[locale]/[...slug]/page.tsx` parsing `slug`
   against the segment map at request time). Rejected for the same reason as
   before: it forces every section through one shared dispatcher file, and
   requires `generateStaticParams` to enumerate entity slugs up front,
   coupling this capability to content data it excludes.

### Unmatched locale prefixes reaching the root 404 is a requirement on `site-shell`, not a mechanism this capability builds

`app/[locale]/layout.tsx` is Dev 2 (INCO)'s `site-shell` file, not
locale-routing's — per `docs/task-assignments.html`, `site-shell` is
explicitly *blocked by* `locale-routing`, meaning it consumes this
capability's exports once they exist, rather than the reverse. This design
specifies the requirement `site-shell` must implement there:
`generateStaticParams` returning only `en`/`tr` (sourced from this
capability's exported `LOCALES` list) alongside
`export const dynamicParams = false`, so a request whose first segment isn't
one of those two never matches the `[locale]` route and falls through to the
root `app/not-found.tsx` — the locale-less fallback page `i18n-hardening`
builds. Because locale-routing does not build `app/[locale]/layout.tsx`, it
cannot itself guarantee this mechanism exists end to end; it specifies the
requirement and supplies the `LOCALES` data `site-shell` needs to satisfy it.
A request that does match a locale but no further route (e.g.
`/tr/olmayan-sayfa`) reaches `app/[locale]/not-found.tsx` instead, also
`i18n-hardening`'s file.

### The switcher's resolution contract has three outcomes, returned as data — Dev 3 supplies the contract, not any UI

Locale-routing owns the *decision logic* behind the switcher — a function
taking the current page's section key (and, for entity pages, per-locale slug
information) and returning a structured result, matching the three
requirements in `specs/localization/spec.md`:

1. **A target-locale slug is available** (section pages always; entity pages
   when the translation and its slug both exist) → `{ kind: 'available', path }`.
2. **CMS-backed content exists in the target locale but has no recorded slug
   there** → `{ kind: 'available', path }` addressed by the *default locale's*
   slug instead (per `design/i18n.md` and `design/content-model.md`). This can
   only apply to Strapi-resident entities; CI makes it impossible for git
   content.
3. **No equivalent content exists in the target locale at all** →
   `{ kind: 'unavailable', homePath, reason }` — a destination plus a reason
   the consuming UI uses to render its own notice. Locale-routing does not
   render anything for this case itself.

Dev 3 owns this resolution function and the segment map it reads from
(`apps/web/lib/i18n/`). Dev 3 does **not** own or implement:
- The switcher's visible markup/component — that is Dev 2 (INCO)'s
  `components/shell/`, which calls this resolution function and branches on
  its result.
- Any visible "not available" notice — rendering `{ kind: 'unavailable', ... }`
  into something a visitor sees is the job of whichever UI/shell/error-surface
  owns that page; locale-routing's job ends at returning the structured
  outcome.
- `app/[locale]/page.tsx` — uncontended until Phase 3 per
  `docs/task-assignments.html`.

### A published route, not a resolved segment, is what the sitemap advertises

A segment-map entry being *resolved* (`lib/i18n/segments.ts`) means it has a
real entity and real localized segments — it says nothing about whether a
page has actually been built for it. As of this change, `resolvedSegments()`
returns 9 sections, and **none of them have a published route anywhere in
the repository** (`find apps/web/app -type d` returns no subdirectories at
all). The original implementation iterated `resolvedSegments()` directly into
`sitemap.ts`, which conflated the two conditions and would have advertised
roughly 18 URLs that all 404 if deployed as-is.

**Correction:** `sitemap.ts` returns an empty list until at least one section
has a published route. `specs/localization/spec.md`'s "Sitemap and robots
cover both locales" requirement now states this explicitly — a resolved
segment-map entry is necessary but not sufficient for sitemap inclusion, and
an empty sitemap is a valid, spec-covered state during incremental rollout,
not a defect.

**This is not permanent — it is a standing obligation, not a closed
question.** When a section's route is published, whichever capability builds
that route must add its entry to `sitemap.ts`. No document assigns this
responsibility explicitly. The closest documented coupling is
`docs/task-assignments.html`'s `seo-analytics` capability (Dev 1, P2), which
is listed as *"Blocked by locale-routing for the sitemap's alternates"* —
but that dependency is about the `alternates.languages` mechanism working
correctly, not about populating individual section entries, so it does not
by itself answer who adds each entry. `docs/workflow.html` §08 sequences
"Sections, one change each" (item 6) after locale-routing (item 3), and
`sitemap.ts` stays Dev 3's owned file per the file-zone table throughout —
so the natural, doc-consistent point of extension is each future section
capability's own proposal adding its entry here as one of its own tasks, the
same way it adds its own route. This is **not decided by this change**: it is
recorded as an open item worth ratifying explicitly (alongside
`docs/workflow.html` §15's other still-"proposed, not ratified" conventions)
rather than assumed. This design does not invent a route-existence tracking
mechanism to automate it, and does not implement any other capability's route
to close the gap itself.

### No new runtime dependency; no animation

This capability introduces no library — routing is native Next.js App Router
config and components. It introduces no animation of any tier (L1/L2/L3). No
new Strapi field is introduced or touched — this capability has no CMS-backed
content of its own (it only defines the *contract* `announcements` and
`alumni-directory` will later use).

Locale-routing is intended to introduce no new runtime dependency and no
client component of its own — the resolution function and segment map are
plain data/logic with no UI. Any client bundle impact comes from whichever
consuming UI integrates it (for example Dev 2's switcher in
`components/shell/`), and that impact should be measured against
`apps/web/budgets.json` during that capability's own implementation, not
estimated here.

## Risks / Trade-offs

- **Next.js API citations were checked against a different patch version than
  the one pinned** (see Context) → mitigate by re-verifying against the
  installed 16.3.1 docs during `/opsx:apply`, before writing any code that
  depends on the more recently-changed APIs (redirect status semantics,
  `params` as `Promise`).
- **This pattern is optional for other capabilities; if some adopt it and
  others pick a different mechanism, the site ends up with two different
  routing patterns side by side** → acceptable per this design's Non-Goals:
  this capability does not mandate a convention on route groups it doesn't
  own. Worth raising at the team's "proposed conventions" ratification
  (`docs/workflow.html` §15) if consistency turns out to matter more than the
  ownership boundary.
- **`?notice=unavailable` left in the URL after a refresh or share** is
  harmless but slightly untidy → acceptable; the spec requires the notice to
  be shown, not that the URL self-clean, and client-side history cleanup would
  be the first bit of client JS this capability needs for no functional gain.
- **This capability's behavior is unobservable end to end until `site-shell`
  ships** — there is no live `/en/...`/`/tr/...` route at all until Dev 2
  implements `app/[locale]/layout.tsx`. Mitigation: this is the expected
  phased build order (`docs/workflow.html` §08 lists locale-routing before
  sections); verification here is limited to the exported functions directly
  (done — see `tasks.md`), with end-to-end scenarios explicitly deferred
  rather than claimed.
- **Resolved: `sitemap.ts` previously advertised every resolved section's
  home page even though none had a published route** (confirmed by
  `find apps/web/app -type d` returning no subdirectories at all). Corrected
  per "A published route, not a resolved segment, is what the sitemap
  advertises" below — see that decision for the ongoing obligation this
  creates.
